# Phase C5.3.8 — Portable Evidence Package: First Vertical Slice

Implement Phase C5.3.8 as the next narrow checkpoint after the completed C5.3.7 corpus-processing and portable-export readiness assessment.

Follow the repository-root `AGENTS.md`.

C5.3.7 found no importer, processing-core, resumability, or schema blocker that must be corrected before beginning a bounded portable-export implementation.

This phase should therefore implement the **smallest useful vertical slice of portable export**.

Do not turn this into a general export subsystem.

Do not run a corpus-wide export.

Do not implement re-import.

Do not start Phase D.

Preserve unrelated working-tree state.

---

## Starting point

C5.3.7 established that the current persisted model already contains the important durable graph needed by a future exporter:

```text
source/import provenance
        │
        ▼
document ─── document_binary ─── file_binary
                                  │
                                  ├── processing_job
                                  │
                                  ├── document_representation
                                  │       ├── artifacts
                                  │       ├── segments
                                  │       └── comparisons
                                  │
                                  └── document_representation_selection
                                          └── selected representation
```

It also established that:

* canonical import is independent of processing;
* unprocessed imported binaries are valid;
* processing can happen later;
* successful representation identity and processing-job state support resumability;
* `file_binary.sha256` is content identity;
* storage location is not content identity;
* evidence and interpretation representations remain semantically distinct;
* partial processing is a valid state;
* some operational conclusions such as applicability and coverage are derived rather than first-class persisted facts.

Do not reopen those architectural decisions unless implementation reveals a concrete contradiction.

---

# Objective

Implement a bounded export operation that can take one selected existing `file_binary` and produce a self-contained portable directory containing enough persisted information to understand that binary and its derived material **without subsequently querying the Virgilio database**.

This means the package contains the evidence, metadata, relationships, and provenance needed to interpret its exported contents.

It does not mean:

* the package must be independently executable;
* the package must reconnect to the source Virgilio installation;
* source storage locations must remain resolvable;
* source-machine filesystem paths form part of portable identity.

Source-storage metadata may be retained where useful as provenance/debug metadata, but package interpretation must not depend on resolving that source storage.

The target proof is:

```text
existing persisted binary
        ↓
bounded exporter
        ↓
portable directory
        ├── manifest
        ├── original binary
        ├── persisted provenance/context
        ├── processing-job history
        ├── persisted representations
        └── persisted representation artifacts
```

The resulting package should preserve identity and provenance rather than merely copying files.

The implementation should prove the package boundary, not finalize the long-term export format.

---

# Core acceptance question

At the end of C5.3.8, answer:

> Can a selected already-imported binary be exported into a standalone directory such that its original evidence, canonical identity/context, persisted processing history, persisted evidence/interpretation representations, and persisted artifacts can be understood and related to each other without querying the source database?

If yes, demonstrate it with a real persisted example.

# Scope: one binary at a time

The primary export unit for this checkpoint is one selected `file_binary`.

Prefer selection by canonical SHA-256 if that fits existing repository conventions.

For example, the CLI may conceptually resemble:

```text
node app/<export-command>.mjs --sha256 <sha256> --output <directory>
```

This syntax is illustrative, not mandatory.

Inspect existing CLI/admin conventions and use the narrowest repository-consistent shape.

Do not implement:

* full corpus export;
* case export;
* workspace export;
* bucket export;
* arbitrary query-based export;
* export scheduling;
* background export jobs.

The data contained in the one-binary package may include all persisted documents/buckets/cases/workspaces that relate to that binary where necessary to preserve provenance.

That does not make those entities independent export roots in this phase.

---

# Package shape

Use a simple directory package.

A reasonable conceptual shape is:

```text
<export-root>/
    manifest.json
    originals/
        <portable-original-name>
    representations/
        <representation-id>/
            ...
```

Additional small subdirectories are allowed where the persisted artifact model makes them useful.

Do not force this exact shape if repository inspection shows a cleaner equivalent.

The requirements are:

1. one clear machine-readable manifest;
2. original binary content is included;
3. persisted representation/artifact content needed by the package is included;
4. manifest references package-relative paths;
5. the package does not depend on source-machine absolute paths.

---

# No archive format yet

Do not add ZIP/TAR packaging unless an existing trivial repository helper makes this effectively free and necessary.

A directory is the portable package for C5.3.8.

Archive/container format is a later concern.

---

# Manifest status

`manifest.json` is a **C5.3.8 package contract**, but not yet a general external interchange standard.

Keep it:

* explicit;
* deterministic where practical;
* versioned;
* understandable;
* narrow.

Include a small package format/version identity, for example conceptually:

```json
{
  "package_format": "virgilio-portable-evidence",
  "package_version": 1
}
```

Use repository-appropriate naming after inspection.

Do not introduce JSON Schema unless implementation demonstrates a concrete need.

Tests can validate the produced JSON structure directly.

---

# Manifest identity principles

Portable identity must come from persisted canonical identity, not filesystem location.

Preserve:

```text
file_binary.sha256
    !=
storage location
```

Do not export source-machine absolute paths as canonical identifiers.

`storage_package_id`, `storage_rel_path`, `artifact_rel_path`, and similar source-storage metadata may be included only where they are useful provenance/debug metadata and clearly distinguished from portable package paths.

The package itself should reference included content using package-relative paths.

---

# Original binary

Include the exact original binary.

Retrieve it through the existing storage abstraction.

Do not:

* directly construct filesystem paths when `BinaryStore` already provides the abstraction;
* expose an internal absolute storage path as portable identity;
* transform/re-encode the original;
* replace it with extracted text.

Validate that the copied binary matches the canonical persisted SHA-256.

Export must fail clearly if the supposedly canonical original cannot be read or does not match its expected identity.

Do not silently produce a package missing its selected original binary.

---

# Canonical provenance/context

For the selected `file_binary`, export enough persisted canonical context to reconstruct its relationships.

Inspect the actual schema and include the relevant persisted data for:

* `file_binary`;
* `document_binary`;
* linked `document`;
* linked `bucket`;
* linked `case_file`;
* workspace linkage where applicable;
* import/source provenance where applicable.

Do not invent missing provenance.

Do not flatten multiple procedural occurrences into one arbitrary document.

If multiple documents or procedural contexts reference the same binary, preserve that multiplicity.

This is important:

```text
one file_binary
    may participate in
multiple document/procedural occurrences
```

The export must not silently collapse those relationships.

---

# Processing history

Keep three categories explicit:

1. **persisted processing/history metadata**

   * serialized from existing repository rows/state;

2. **package-local copied content**

   * original binary and persisted representation artifacts copied into the portable package;

3. **exporter-derived convenience information**

   * summaries or classifications reproducibly computed at export time from persisted state/current policy.

Do not mix these categories in a way that makes copied files or exporter-derived summaries appear to be independently persisted database facts.

Export the persisted `processing_job` rows relevant to the selected binary.

Use repository-accurate terminology.

Include persisted fields needed to understand the processing history, such as where available:

* job identity;
* stage;
* processor key;
* processor version;
* persisted status;
* timestamps;
* persisted retry/attempt-count fields;
* persisted error code/text;
* produced representation relationship.

Do not invent a separate execution-attempt entity.

Do not synthesize a richer attempt-event history than the repository actually persists.

If timeout attribution is included, distinguish clearly between:

* persisted status/error information;
* exporter-derived classification.

Do not represent `timed_out` as a persisted status if it is not one.

---

# Representations

Include all persisted representations associated with the selected binary that are reachable through the current representation/artifact model.

Use existing repository relationships such as `document_representation`, `artifact_rel_path`, `document_segment`, and other current persisted representation relationships discovered during inspection.

Do not scan for or resurrect legacy, stray, temporary, or otherwise untracked filesystem outputs merely because files happen to exist on disk.

The database/current artifact model remains authoritative for deciding what belongs to the exported representation set.

Preserve at least:

* representation id;
* representation kind;
* processor key;
* processor version;
* source binary relationship;
* creation/provenance metadata already persisted;
* representation artifact metadata;
* segment/text information where applicable.

Do not export only the currently preferred representation.

The package should preserve the available persisted evidence/interpretation set.

---

# Evidence versus interpretation

Preserve the semantic distinction established by earlier phases.

In particular, do not flatten:

```text
original PDF
    !=
pdf_literal_text
    !=
pdf_signature_metadata
    !=
pdf_structure_inventory
    !=
pdf_ocr_text
    !=
Docling interpretation
    !=
Xberg interpretation
```

The manifest must retain enough representation identity/provenance to determine what each exported derived item actually is.

Do not produce anonymous files such as:

```text
text.txt
```

whose origin and semantics cannot be recovered from the package.

Human-friendly filenames are fine, but the manifest remains authoritative for identity/provenance.

---

# Representation artifacts

Copy persisted representation artifacts that are part of the exported representation state.

Use existing representation-artifact access/resolution logic where possible.

Do not create new derived artifacts during export.

Export is read-only with respect to evidence/processing state.

If a representation has:

* markdown;
* complete text;
* native JSON;
* evidence text;
* structure/signature JSON;
* other already-persisted artifacts;

include them according to the existing persisted artifact model.

Do not run Docling, Xberg, OCR, qpdf, pdftotext, or any processor to fill a missing artifact.

---

# Segment-backed content

Inspect how `document_segment` content relates to representations.

If persisted representation meaning would be materially incomplete without segment-backed text/content, include it in the manifest or as a package artifact in the narrowest sensible form.

Do not duplicate large content unnecessarily merely because it exists in both an artifact and segments.

Document the chosen rule.

---

# Selection and comparison information

Where persisted for the selected binary/representations, include:

* explicit representation selection rows;
* persisted representation comparisons.

Do not create a new selection.

Do not infer that the effective consultation selection is itself a persisted fact when it is derived.

If an effective-selection summary is included for convenience, label it explicitly as derived.

The persisted selection data and any derived effective-selection assessment must remain distinguishable.

---

# Persistence versus derived assessment

Maintain the C5.3.7 distinction throughout the package.

Every material exported concept should fall into one of:

### Persisted

Directly backed by repository state.

Examples:

* canonical entities/relationships;
* `processing_job` rows;
* representations;
* artifacts;
* explicit selections;
* persisted comparisons.

### Derived at export time

Computed reproducibly from persisted state and current repository policy.

Possible examples:

* processor applicability;
* coverage summary;
* timeout-attributed failure classification;
* effective consultation selection.

### Not available

Information that is neither persisted nor reliably reconstructible.

Do not silently promote derived information into persisted historical fact.

A simple manifest-level distinction or clearly separate sections is preferable to subtle per-field complexity.

Do not overengineer a generalized provenance ontology.

---

# Coverage/applicability summaries

Coverage summaries are optional in C5.3.8.

The portable-package proof does not require a generalized processing-coverage engine.

If an existing helper makes a useful per-binary summary straightforward, it may be included as explicitly derived information.

Otherwise defer it.

Do not create new persistence for:

* `not_applicable`;
* `not_scheduled`;
* corpus rollout membership;
* rollout completeness.

---

# Partial processing

The exporter must work correctly for partially processed binaries.

For example:

```text
original                 present
literal evidence         present
signature metadata       present
Docling                  failed
Xberg                    completed
OCR                      not applicable
```

must still be a valid export.

Likewise, a canonically imported but completely unprocessed binary should remain conceptually exportable.

Additionally, require one explicit focused validation or test using a canonically imported binary with no processing jobs or representations, if the current DB/test fixtures provide one.

Verify that such a binary exports successfully with:

* canonical binary identity;
* exact original binary;
* applicable canonical/document/procedural/source provenance;
* an honestly empty processing/representation set.

The exporter must not interpret absence of processing as an export failure.

However, the primary validation example for this phase should be a binary with sufficiently rich persisted derived material to prove the vertical slice.

Do not treat missing processing as an export failure.

The selected original binary being unreadable or failing SHA validation is different: that is an integrity failure and should fail the export.

---

# Determinism

Aim for deterministic output where practical.

Given unchanged persisted state and the same selected binary:

* manifest ordering should be stable;
* entity/representation/job arrays should have deterministic ordering;
* package-relative naming should be stable;
* repeated export should not arbitrarily change identifiers.

Do not require byte-identical manifests if unavoidable export timestamps are deliberately included.

Prefer avoiding volatile fields that provide no useful provenance.

If an export-generation timestamp is included, distinguish it from source/persisted timestamps.

---

# Collision-safe filenames

Do not rely on source filenames being unique.

Portable package paths must be collision-safe.

Prefer canonical identity or representation identity where appropriate.

For the original binary, a human-readable filename may be used if it remains unambiguous and the manifest maps it to canonical SHA identity.

Do not mutate the original binary content.

---

# Output-directory safety

Do not overwrite unrelated existing files silently.

Use a narrow, predictable output-directory policy.

Prefer either:

* require the target package directory not to exist; or
* require it to be empty.

If repository conventions suggest another safe policy, document it.

Do not implement complex incremental export merging in this phase.

---

# Read-only guarantee

The exporter must not mutate canonical/processing state.

It must not:

* enqueue jobs;
* run processors;
* create representations;
* create segments;
* change selections;
* create comparisons;
* update processing jobs;
* alter importer/source state.

Add a focused test or validation proving that export does not create processing work or representation state.
