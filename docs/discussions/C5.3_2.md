# C5.3 PDF Evidence Extraction Investigation Findings

Source prompt:

- `docs/discussions/C5.3_1.md`

Run date:

- `2026-09-01`

## 1. Executive Conclusion

Observed corpus and tool behavior confirms that the current interpretation engines are **not** sufficient as Virgilio's PDF evidence boundary.

Docling and Xberg remain useful interpretation engines, but they do not expose all evidence-bearing channels present in the PDF binary. The regression case `6836f8732aae33a3bc79491748134bd2a77a7b48aeaa2cd7c66647ff1f468f1c` proved the point directly:

- visible signature-appearance text is present in the PDF;
- `pdftotext` exposes it;
- Docling does not expose it in normal text, `BODY + FURNITURE`, `force_backend_text`, or forced full-page OCR;
- Xberg does not expose it in extracted text even with annotation/form extraction enabled;
- Xberg does expose the existence of the signature field structurally.

Recommended architectural distinction:

- `PDF evidence extraction` answers what evidence-bearing channels exist in the immutable binary and preserves them with provenance.
- `Document interpretation` answers how downstream humans and systems should read or use the document.

That distinction is the safer baseline for sensitive court records.

## 2. Proposed PDF Evidence-Extraction Contract

Authoritative input:

- immutable `file_binary` PDF bytes identified by canonical SHA-256

Expected behavior:

- inspect the PDF conservatively and reproducibly
- expose evidence-bearing channels independently rather than forcing them into one text model
- preserve provenance for every derived artifact
- record when a channel is absent, unavailable, or not attempted

Evidence-channel concept:

- each channel represents a distinct route by which evidence can exist in the PDF
- channels may overlap without being equivalent
- absence from one channel is not evidence of absence from the binary

Minimum provenance for any future persisted evidence artifact:

- source binary SHA-256
- extractor/tool identity
- extractor/tool version
- configuration/profile
- artifact kind / channel identity
- generated timestamp where relevant
- reproducibility notes if output is not byte-stable

Treatment of optional/missing channels:

- channel absence should be explicit
- unsupported channel extraction should remain distinguishable from confirmed absence

Extraction versus interpretation:

- evidence extraction preserves what the binary contains
- interpretation produces human- or downstream-oriented readings such as Docling Markdown, Xberg text, tables, reading order, or future search text

Extraction versus validation:

- extracting signature/certificate structures is distinct from cryptographic validation
- cryptographic validation is distinct from legal validity

## 4. Channel Inventory

Observed channels in the sampled corpus:

Common:

- native/literal PDF text in ordinary text PDFs
- document metadata: producer, creator, page count, PDF version, tagging, AcroForm indicator
- generator diversity across tribunal, scanner, Office, print-driver, and repackaged PDFs

Occasional:

- positional/layout PDF text useful via `pdftotext -layout`
- annotations token presence
- AcroForm presence
- digital-signature fields and signature dictionaries
- page-raster content requiring OCR

Rare but important:

- signature-appearance text that is visible and extractable at the PDF layer but absent from interpretation-engine text
- multi-signature PDFs
- embedded-file candidates

Observed as channel classes but not fully exercised by current tooling:

- certificate metadata
- embedded-file extraction
- incremental revisions associated with signed PDFs

Not observed in this investigation:

- XFA forms

Key silent-omission findings:

- signature appearance text can be visible and recoverable from the binary while remaining absent from Docling and Xberg text
- Xberg can expose the existence of a signature field without surfacing the visible signature block text
- OCR and interpreted text are not interchangeable with native PDF text

## 6. Digital-Signature Findings

Corpus observations:

- binary-token survey across all retained PDFs found about `376` PDFs containing both `/Sig` and `/ByteRange`
- about `386` PDFs contained `/AcroForm`
- multi-signature candidates are real, not hypothetical:
  - `0e661625...` -> 2 `/ByteRange`
  - `d53fe053...` -> 3 `/ByteRange`
  - `a74153f1...` -> 6 `/ByteRange`
  - `f5f9bb87...` -> 11 `/ByteRange`

Regression case `6836f873...`:

- exactly one signature field: `Signature1`
- visible text:
  - `Assinado em 13-01-2022, por`
  - `Maria de Fátima Estudante Morgado da Silva, Juiz de Direito`
- visible text originates from the signature widget appearance chain, not ordinary page body content
- current Docling and Xberg text outputs omit it
- `pdftotext` exposes it
- Xberg exposes the signature form field structurally

Earlier focused inspection on `6836f873...` established:

- `/ByteRange` present
- `/M` signing timestamp present
- `/Name`, `/Reason`, `/ContactInfo` present
- certificate subject, issuer, serial, and fingerprints are extractable by low-level signature tooling

Implications:

- signature evidence is at least a three-channel problem:
  - visible signature appearance text
  - form/signature structural metadata
  - certificate/signature cryptographic metadata
- these channels overlap but are not equivalent
- a later extraction slice should preserve them distinctly

Multiple-signature and revision implications:

- repeated `/ByteRange` markers strongly suggest incremental signed revisions or multiple signed objects in some PDFs
- this investigation did not perform full revision-chain extraction
- revision-aware signature handling is real but should not be the first implementation slice

Operational limitation:

- Linux/WSL `pdfsig` would be useful for certificate/signature extraction, but on this machine the current `wsl.exe` probe failed with `E_ACCESSDENIED`
- Linux userland or a pinned container remains a relevant operational option for later reproducible signature tooling

## 7. Literal-Text Findings

Observed value of low-level literal text:

- `pdftotext -layout` recovers visible signature-appearance text that both interpretation engines omit on `6836f873...`
- `pdftotext -layout` returned meaningful full-document literal text for signed text PDFs such as `f5f9bb87...`, including repeated visible signature blocks and ordinary page text
- `pdftotext` returned no usable text for the image-only sample `02c8e7ce...`, confirming that literal PDF text and OCR are distinct channels

Observed limits:

- `pdftotext` is not authoritative reading order or semantic structure
- repeated headers, footers, and signature blocks can dominate literal output
- scan-only PDFs need OCR or page-raster handling, not literal-text extraction

Recommendation:

- a separate low-level literal-text representation is justified as a first-class evidence artifact
- it should be named and documented as a channel-specific artifact, not implied to be a complete or canonical human reading

## 8. Observed Corpus Patterns

Supported patterns:

- digitally signed PDFs are common enough in this corpus to deserve first-slice attention
- PDF generators vary materially:
  - `CITIUS` / `Citius`
  - Microsoft Word / Microsoft Print to PDF
  - `iTextSharp`
  - `PrimoPDF`
  - `Canon` and `VersaLink` scanner/printer generators
  - `iLovePDF`
  - `doPDF`
  - `ABCpdf`
  - `DXperience`
- image-only and mostly-image PDFs are common enough to require a deliberate OCR-capable path
- some scan-heavy PDFs appear to be page rasters without native text
- visible signature appearance text can coexist with structured signature data and ordinary body text

Plausible but not fully proven patterns:

- some multi-signature PDFs likely correspond to incremental signed revisions rather than just multiple independent widgets
- the small embedded-file candidate set may cluster in a particular producer family (`DXperience`), but that needs a narrower follow-up before claiming a real pattern

## 9. Recommended Smallest Implementation Slice

The next bounded implementation phase should focus on the smallest set of durable evidence artifacts that materially reduce silent evidence loss without redesigning the entire PDF model.

### Persisted artifacts

1. `pdf-literal-text`

- purpose: preserve recoverable literal PDF text independently from Docling/Xberg interpretation
- source channel: native/literal PDF text
- provider/tool: Poppler `pdftotext`, probably with a documented layout-oriented mode
- provenance:
  - source binary SHA-256
  - tool identity/version
  - mode/configuration
- production:
  - every PDF where literal text extraction succeeds
  - explicit empty/absent outcome where no literal text exists
- identity/versioning:
  - distinct from Docling/Xberg text artifacts
  - do not reuse `text.txt` or `complete-text.txt`
- why first slice:
  - directly addresses the proven silent-omission case on signed PDFs
  - cheap to generate
  - reproducible

2. `pdf-signature-metadata`

- purpose: preserve signature/form/certificate facts that ordinary text extraction does not express
- source channel: AcroForm/signature structures and certificate metadata
- provider/tool: low-level PDF/signature tooling
- provenance:
  - source binary SHA-256
  - extractor identity/version
  - whether facts came from signature dictionary, appearance structure, or certificate layer
- production:
  - conditional; only for PDFs with signature fields or signature dictionaries
- identity/versioning:
  - dedicated artifact, not merged into text output
- why first slice:
  - signatures are common in the corpus
  - missing this channel is materially risky for court evidence

3. `pdf-structure-inventory`

- purpose: persist a small inventory of which evidence channels the PDF contains
- source channel: low-level PDF structure inspection
- provider/tool: qpdf/pdfinfo plus narrow custom glue
- provenance:
  - source binary SHA-256
  - tool versions
  - inspection profile
- production:
  - every PDF
- identity/versioning:
  - small normalized/JSON artifact; do not turn it into a huge forensic dump
- why first slice:
  - lets downstream systems know whether the PDF had signatures, forms, annotations, embedded files, page rasters, and similar channels
  - prevents silent absence assumptions

4. conditional `ocr-text`

- purpose: preserve rendered-page text when native PDF text is absent or insufficient
- source channel: rendered-page OCR text
- provider/tool: existing local OCR-capable processor path
- provenance:
  - OCR engine identity/version
  - OCR mode/configuration
  - language settings where relevant
- production:
  - conditional for `image_only_pdf`, `mostly_image_pdf`, and selected `mixed_pdf`
- identity/versioning:
  - explicit OCR artifact, not treated as native PDF text
- why first slice:
  - image-only PDFs are common
  - needed for completeness, but should remain distinct from native text

### Non-persisted diagnostics

- raw qpdf object dumps
- ad hoc appearance-stream extraction traces
- verbose parser stderr
- one-off comparison snippets used to classify omissions
- temporary rendered page images used only for troubleshooting

These are useful during validation and tool development but do not currently justify durable persistence.

### Deferred channels

1. embedded-file extraction

- why deferred:
  - only a small candidate set observed
  - current local tooling path was not yet clean enough to recommend durable extraction
- reconsider when:
  - a targeted follow-up confirms actual attachments with corpus relevance
- preservation basis:
  - immutable original PDF is sufficient for later extraction

2. revision-chain / incremental-signature analysis

- why deferred:
  - clearly relevant for some signed PDFs but deeper than the first loss-reduction slice
- reconsider when:
  - signature-aware downstream use requires distinguishing signing generations
- preservation basis:
  - original binary retains the revision chain

3. generalized annotation-content extraction

- why deferred:
  - annotations occur, but the regression case showed signature appearance is the clearer first risk
- reconsider when:
  - annotation-bearing cases materially affect consultation or retrieval
- preservation basis:
  - original binary remains sufficient

## Recommendation

Do **not** continue patching `complete-text.txt` in place.

The next implementation slice should establish a small PDF evidence-extraction layer that persists:

- literal PDF text
- signature metadata
- a compact structure inventory
- conditional OCR text

Docling and Xberg should remain downstream interpretation layers over that evidence, not the authoritative evidence boundary.
