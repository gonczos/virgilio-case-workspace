# C5.3.2 framing note

Date:

* `2026-09-01`

Purpose:

* record the agreed refinement for the next PDF-evidence phase after the completed C5.3.1 checkpoint

## Agreed correction

The next step should **not** be framed as a second broad investigation into whether the newly surfaced PDF evidence channels matter.

That question is already answered strongly enough by the completed C5.3 investigation and the C5.3.1 implementation checks:

* signed PDFs are common in the corpus;
* image-only and mostly-image PDFs are materially present;
* literal PDF text can recover evidence omitted by Docling/Xberg interpretation artifacts;
* PDF evidence channels such as visible signature appearance text, signature structure, and OCR-derived text are distinct and should remain distinct.

## Recommended next-phase framing

Use:

* `C5.3.2 — targeted rollout and implementation validation`

Do **not** turn C5.3.2 into:

* a second C5.3 investigation phase;
* an automatic jump into consultation/UI exposure;
* a general search/AI phase.

## C5.3.2 questions

The next bounded phase should answer:

1. Does the C5.3.1 implementation produce the intended artifacts reliably across representative PDF classes?
2. Are artifact semantics and provenance correct in practice?
3. How often does `pdf_literal_text` materially add evidence beyond the current interpretation artifacts?
4. Does the current OCR gating policy behave correctly on:
   * `image_only_pdf`
   * `mostly_image_pdf`
5. Are signature and structure inventories accurate across:
   * ordinary PDFs
   * signed PDFs
   * multi-signature PDFs
   * unusual/problematic PDFs
6. Are there concrete failure modes that justify correcting C5.3.1 before broader rollout?
7. Which deferred evidence channel, if any, is now the next highest-value implementation target?

## Tooling boundary

Minimal CLI/inspection support is reasonable, but it should remain:

* validation tooling;
* rollout/coverage tooling;
* artifact/provenance inspection tooling.

It should **not** become:

* consultation UX;
* viewer work;
* search consumption;
* new representation-selection semantics.

Reasonable examples:

* list evidence artifacts for a binary;
* show artifact metadata/provenance;
* compare artifact text lengths/hashes;
* print a compact channel summary.

## Roadmap discipline

Do not precommit the follow-up after C5.3.2.

Use this sequence instead:

1. `C5.3.2` targeted rollout and implementation validation
2. decision checkpoint based on observed coverage and failure modes
3. then choose one narrow next step:
   * broader evidence rollout;
   * one specifically justified deferred evidence channel;
   * consultation-side exposure of evidence artifacts
4. only after the evidence boundary is stable:
   * search / retrieval / AI-oriented derived work

## Practical rationale

The key distinction is:

* C5.3 already established that these channels matter;
* C5.3.2 should establish how well the implemented boundary behaves across real repository files and where the first implementation policy is insufficient.

That keeps the project on the same cautious path:

* evidence boundary first;
* validate the actual implementation on real files;
* then decide the next narrow step from observed behavior rather than assumption.
