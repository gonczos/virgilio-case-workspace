C4 has been split into:

```text
C4.1  Consultation backend/read models

```

The current runtime shape is:

```text

    ├── canonical corpus
    ├── processing jobs
    ├── representations
    ├── segments
    ├── comparisons
    └── selections

    └── effective-selection/comparison/attention logic

    └── /binary/<sha256>

            ├── native.json
```

Directus remains the raw/admin consultation surface.

The custom consultation API should provide the curated human-facing read models.

# Important C4.1 design principle

The consultation API is a READ MODEL.

It must not become another canonical/domain model.

It may:

* aggregate canonical relationships
* summarize processing state
* call existing representation-selection logic
* expose safe representation content

It must not:

* duplicate canonical facts into new tables
* persist UI-specific summaries
* redefine selection semantics
* mutate representation state
* infer semantic/legal facts that are not already persisted

# HTTP implementation approach

Use the smallest HTTP approach consistent with the repository.

There is no requirement to introduce Express, Fastify, Nest, or another framework merely for this slice.

Prefer existing Node runtime patterns unless repository evidence demonstrates that a small dependency materially simplifies the implementation.

If practical, share reusable server utilities between the consultation API and `file-gateway`, but do not refactor the gateway broadly.

Keep the implementation easy to replace later.

# Catalogue context aggregation

Remember:

```text
file_binary != document
```

Current corpus contains binaries linked to multiple:

* documents
* buckets
* cases

So catalogue aggregation must correctly handle multiplicity.

At minimum aggregate through:

```text
file_binary
    -> document_binary
    -> document
    -> bucket_document
    -> bucket
    -> case_file
```

Use `DISTINCT` appropriately.

Do not multiply counts accidentally due to joins.

Validate the known multiplicity cases.

# Catalogue display-name policy

Implement a small deterministic display-name helper.

Recommended behavior:

## One linked document

Use its document name where available.

## Multiple linked documents, one common non-empty name

Use the common name.

Expose the document count separately.

## Multiple distinct names

Use:

```text
Multiple linked documents
```

and include the individual names in `linked_document_names`.

## No usable linked document name

Use a compact fallback based on available binary metadata, for example:

```text
PDF <sha-prefix>
```

Do not use a full SHA as the primary human label.

Keep the helper deterministic and unit-testable.

# Critical artifact-path safety boundary

DO NOT expose arbitrary artifact filesystem paths.

DO NOT accept:

```text
?path=...
```

DO NOT allow callers to request arbitrary filenames.

The caller may identify only:

```text
representation id
+
allowlisted logical format
```

For example:

```text
text
markdown
native-json
```

The backend resolves the actual artifact internally.

---

# Text content

For:

```text
format=text
```

prefer persisted:

```text
document_segment.text_content
```

rather than reading `text.txt` from disk.

Reasons:

* PostgreSQL already contains the normalized text
* it avoids unnecessary filesystem coupling
* it makes text retrieval consistent across processors
* human/plain-text representations can use the same path

If several segments later exist, concatenate/order using:

```text
sequence_no
```

Do not assume forever that each representation has one segment.

Preserve deterministic segment ordering now.

---

# Markdown content

For:

```text
format=markdown
```

support only representations where a retained Markdown artifact actually exists.

Current expected case:

```text
Docling -> markdown.md
```

Resolve the artifact internally from the representation's persisted artifact location.

Return 404 or another clear safe response when the requested format does not exist.

Do not synthesize Markdown from plain text.

---

# Native JSON content

For:

```text
format=native-json
```

read the retained `native.json` artifact where available.

Parse and return valid JSON if practical.

If the artifact is malformed unexpectedly:

* do not crash the server
* return a safe representation-artifact error
* preserve diagnostics in server logs if logging exists

Do not substitute `content_json` for native processor JSON.

They have different semantics.

---

# Artifact storage safety

Representation artifacts are derived data and are currently local filesystem artifacts.

Introduce only a narrow READ helper if needed.

For example:

```text
resolveRepresentationArtifact(...)
readRepresentationArtifact(...)
```

Requirements:

* resolve only from persisted representation metadata
* validate resolved paths remain inside the expected processing-artifact root
* reject path traversal
* allow only known filenames/formats
* verify readable file
* never return resolved absolute filesystem paths to the client

Do not build a general ArtifactStore abstraction in C4.1 unless an existing boundary already exists and reusing it is trivial.

A broader artifact-storage abstraction is still deferred.

# Performance

The corpus is currently small enough that premature optimization is unnecessary.

However:

* avoid obvious N+1 queries across ~1238 binaries
* do not call several independent DB queries per catalogue row
* aggregate canonical catalogue context in bulk/query form
* processing-state enrichment may be composed efficiently on the server

If the most natural first implementation needs a small number of bulk queries plus in-memory combination, that is acceptable.

Do not create a cache layer.

Do not add Redis.

Do not add materialized views unless measurement demonstrates a need.
