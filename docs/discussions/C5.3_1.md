# C5.3 — PDF Evidence Extraction Investigation

### Naming

Create the investigation prompt as:

`docs/discussions/C5.3_1.md`

Treat C5.3 as a new bounded investigation phase following the completed and committed C5.2 checkpoint.

## Objective

Perform a bounded design/investigation pass to establish the **PDF evidence-extraction boundary** for Virgilio.

Do not implement a new extraction architecture yet.

The purpose of this phase is to determine, from the actual corpus and current repository/tooling, what evidence-bearing information can exist in PDFs, which local tools expose each channel, where silent omissions occur, and what the smallest defensible implementation slice should be.

The architectural premise for this investigation is:

* the original PDF binary is authoritative and immutable;
* Docling and Xberg are **document interpretation engines**, not authoritative evidence extractors;
* binary-near PDF evidence extraction is a separate concern;
* downstream search, semantic extraction, taxonomy, summarization, and legal interpretation must remain outside this scope.

The expected outcome is a concrete design recommendation grounded in observed corpus evidence.

---

## Context

Recent C5.2 work improved preservation of document text that had previously been omitted as headers/footers/furniture.

However, inspection of the PDF with SHA-256:

`6836f8732aae33a3bc79491748134bd2a77a7b48aeaa2cd7c66647ff1f468f1c`

showed a more fundamental limitation.

The PDF visibly contains:

`Assinado em 13-01-2022, por`

and the signer name/title.

Observed behavior in the current repository:

* `pdftotext` extracts this text;
* Docling does not expose it in its normal output;
* Docling still does not expose it with:

  * BODY + FURNITURE;
  * `force_backend_text = True`;
  * forced full-page OCR;
* Xberg does not expose it in extracted text;
* Xberg still does not expose it with:

  * `extract_annotations=True`;
  * `extract_form_fields=True`;
* Xberg does expose a form field:

  * `field_type = "signature"`
  * `full_name = "Signature1"`

Additional inspection indicates that the PDF contains real PDF text associated with the visible signature appearance, while signature/form structures expose related information through a different channel.

This demonstrates that:

1. interpreted document text is not necessarily a complete inventory of evidence contained in the PDF;
2. literal PDF text, forms/annotations/signature structures, certificate information, rendered content, and OCR may represent separate evidence channels;
3. no current interpretation engine should be assumed to provide an exhaustive primary extraction.

Do not solve only this one PDF. Use it as a regression/example case exposing the broader architectural problem.

# Required architectural distinction

Use the following conceptual separation throughout the investigation.

## A. PDF evidence extraction

Question:

> What evidence-bearing information is actually present in the source PDF binary?

This is binary-near, conservative, reproducible extraction.

Possible channels include, but are not limited to:

* native/literal PDF text;
* positional/layout PDF text;
* annotation/signature-appearance text;
* rendered-page OCR text;
* page images and other raster content;
* annotations;
* widgets;
* AcroForm fields;
* digital-signature fields;
* signature dictionaries;
* certificate metadata;
* PDF document metadata;
* embedded files;
* incremental revisions;
* other structural diagnostics that prove useful in this corpus.

Keep these distinctions explicit.

In particular:

* literal PDF text is not equivalent to OCR text;
* annotation/signature-appearance text is not automatically equivalent to ordinary page-content text;
* OCR output is evidence derived from rendering, not native PDF text;
* visible signature appearance is not equivalent to the underlying cryptographic signature structure.

This phase does **not** interpret the legal meaning of those facts.

## B. Document interpretation

Question:

> How should downstream systems read and use the document?

Examples:

* Docling;
* Xberg;
* reading order;
* headings;
* tables;
* Markdown;
* reconstructed document structure;
* later legal taxonomy;
* semantic entities;
* summaries;
* search-oriented text.

These are derived interpretations and may legitimately differ from one another.

They must not be treated as authoritative evidence inventories.

# Scope

## In scope

### 1. Define a PDF evidence-extraction contract

Produce a proposed conceptual contract describing:

* input;
* evidence channels;
* provenance requirements;
* reproducibility requirements;
* treatment of absent channels;
* distinction between raw extraction and interpretation;
* distinction between extraction and validation.

Do not prematurely design a large relational schema.

The contract should be precise enough to guide the next implementation slice.

### 2. Select an intentionally adversarial sample of approximately 20–30 PDFs

Do not use a purely random sample.

Select PDFs likely to exercise different PDF structures and failure modes.

Prefer examples including, where available:

* known digitally signed PDFs;
* PDFs with multiple signatures;
* old tribunal/Citius-generated PDFs;
* newer tribunal/Citius-generated PDFs;
* image-only scanned PDFs;
* mixed native-text + scanned-page PDFs;
* PDFs with forms/widgets;
* PDFs with annotations;
* files produced by different PDF generators;
* files with visible stamps/marginal text;
* PDFs already known to differ between Docling/Xberg/pdftotext;
* derivative/repackaged PDFs if identifiable;
* malformed or unusual PDFs where useful.

Include:

`6836f8732aae33a3bc79491748134bd2a77a7b48aeaa2cd7c66647ff1f468f1c`

as a mandatory regression/example case.

Record why each selected PDF was included.

### 3. Inventory evidence channels present in the sample

For each sampled PDF, determine whether the following exist where reasonably detectable:

* native PDF text;
* positional/layout text;
* page images;
* OCR-only content;
* headers/footers/marginal text;
* annotations;
* form fields/widgets;
* signature fields;
* cryptographic signature data;
* certificate metadata;
* document metadata;
* embedded files;
* incremental revisions;
* other relevant structural features discovered during inspection.

The goal is not exhaustive PDF forensics.

The goal is to identify the evidence-bearing channels that actually occur in this corpus.

### 4. Build a channel/tool coverage matrix

Evaluate the existing/local tooling against the observed channels.

At minimum inspect relevant capabilities of tools already present or easily available in the repository environment, such as:

* Docling;
* Xberg;
* Poppler / `pdftotext`;
* qpdf;
* existing Python PDF libraries already used by the project;
* existing OCR facilities;
* other already-installed low-level PDF utilities if relevant.

Do not add a large new dependency merely to make the matrix comprehensive.

For each channel/tool combination, record where appropriate:

* reliably exposed;
* partially exposed;
* not exposed;
* unclear;
* configuration-dependent;
* silently omitted;
* structurally visible but not available in extracted text.

Pay particular attention to **silent omission**, because this is more dangerous for this system than imperfect formatting.

### 5. Investigate digital signatures as an evidence channel

This deserves deliberate attention, but keep it bounded.

Determine what can be extracted from signed PDFs in the corpus, including where present:

* signature field name;
* whether the field is populated;
* `/ByteRange`;
* signature dictionary presence;
* signing timestamp fields;
* signer/name fields;
* reason/location/contact fields;
* certificate subject;
* certificate issuer;
* certificate serial number;
* certificate fingerprint;
* signature algorithm/digest information where easily available;
* signature appearance streams;
* relationship between visible signature-appearance text and underlying signature structure;
* presence of multiple signatures;
* evidence of incremental revisions associated with signing.

Do **not** perform legal conclusions about signatures.

Do **not** build full PKI/trust-chain validation unless a very small diagnostic is necessary to understand the structure.

In particular, keep separate:

* extraction of signature/certificate facts;
* cryptographic validation;
* trust decisions;
* legal validity.

### 6. Investigate literal PDF text separately from interpreted text

Determine whether a low-level literal text representation is needed as a first-class artifact.

Compare at least:

* Docling text;
* Xberg text;
* `pdftotext` plain/raw behavior where useful;
* `pdftotext -layout` or equivalent positional projection where useful;
* OCR output where relevant.

Do not attempt to silently merge them.

Do not treat `pdftotext` output as authoritative reading order or semantic document structure.

Its purpose in this investigation is to determine what literal/native PDF textual content it can expose that higher-level interpretation engines may omit.

Where `pdftotext`, Docling, Xberg, OCR, or appearance-stream extraction disagree, preserve the distinction and determine which PDF evidence channel each result represents rather than selecting one output as universally authoritative.

Determine what each representation is actually good at preserving.

Explicitly test known omissions such as the signature-appearance text in `6836f873...`.

### 7. Record provenance requirements

Recommend the minimum provenance required for any future extracted artifact.

Consider at least:

* source binary SHA-256;
* extractor/provider;
* extractor version;
* configuration/profile;
* representation/artifact identity;
* generation timestamp if appropriate;
* deterministic/reproducible status;
* relationship to the immutable binary.

Do not overdesign generalized provenance infrastructure if it is not needed yet.

The goal is to establish what information must not be lost.

# Design principles to evaluate

Use these as hypotheses/design constraints and confirm or revise them based on the investigation.

### Preserve before interpreting

The immutable binary remains authoritative.

Derived representations must never replace it.

### No single interpretation engine is authoritative

Absence from Docling or Xberg is not evidence of absence from the PDF.

### Do not silently merge evidence channels

If native text, OCR text, annotation text, or signature-appearance text disagree or differ, preserve their provenance.

### Avoid unjustified claims of completeness

Do not call an artifact `complete-text` unless completeness has a precise, testable definition.

Prefer channel-specific terminology such as:

* `pdf-literal-text`;
* `ocr-text`;
* `docling-text`;
* `xberg-text`;
* `signature-metadata`;
* `annotation-data`;
* later `search-text`.

These are examples, not mandatory final names.

### Preserve raw values before normalization

Especially for:

* identifiers;
* certificate subjects;
* timestamps;
* PDF metadata;
* signature fields;
* form values.

### Extraction is not validation

Extracting a signature or certificate does not imply that it has been cryptographically, legally, or institutionally validated.

### Silent omission is a first-class failure mode

For this corpus, losing small pieces of evidence can be more serious than producing imperfect reading order or formatting.

# Constraints

Do not:

* implement the next extraction system yet;
* modify C5.2 behavior unless required for a diagnostic;
* change representation identity semantics;
* silently redefine existing artifacts;
* introduce semantic/legal extraction;
* introduce document taxonomy;
* introduce search aggregation;
* add message brokers, queues, workers, frameworks, or unrelated infrastructure;
* perform broad refactoring;
* add large dependencies without a clear investigation need;
* mutate source PDFs;
* fabricate evidence when an extraction channel is absent;
* treat `pdftotext` output as authoritative reading order, document structure, or semantic interpretation;
* assume that information exposed by one evidence channel should automatically be copied into another;
* persist diagnostic output merely because a tool can produce it;
* implement every observed PDF feature; distinguish persisted evidence, diagnostics, and explicitly deferred channels;
* treat OCR output as equivalent to native PDF text;
* treat visible signature text as equivalent to cryptographic signature metadata;
* treat cryptographic validation as equivalent to legal validity.

Keep the work diagnostic and design-focused.
