# Diagnostic: Prove Header / Footer Reference Preservation Behavior

We have observed that some legally important reference data in court PDFs — especially case numbers, filing references, dates, and other identifiers near the top of the page — is missing or de-emphasized in the text representation produced by Docling and, in some cases, Xberg.

`pdftotext -layout` appears to preserve some of this information better.

Before adding another extractor or changing the processing architecture, investigate and prove exactly where this information is being lost.

## Scope

This is a diagnostic/proof task only.

Do **not**:

* change the production extraction pipeline
* add `pdftotext` as a processor
* change database schemas
* change API contracts
* change the C4.2 consultation UI
* introduce new architectural abstractions
* refactor unrelated processing code
* start a new implementation phase
* commit implementation changes merely to demonstrate the result

Temporary diagnostic scripts/files are acceptable if clearly isolated and easy to remove.

## 1. Inspect the exact installed versions and APIs

First determine the exact Docling and Xberg versions used by the current repository/environment.

Inspect both:

* our adapter/integration code
* the actually installed library APIs

Do not rely solely on generic online documentation, because behavior and configuration options may differ by version.

For Docling, determine:

* whether the extracted `DoclingDocument` contains `BODY` and `FURNITURE` content layers
* whether page headers and footers are represented as `FURNITURE`
* whether our current export/projection excludes `FURNITURE`
* whether we can iterate/export both layers without modifying extraction itself
* whether any relevant header/footer/furniture configuration exists in the installed version

For Xberg, determine:

* whether the installed version exposes `ContentFilterConfig` or equivalent
* whether it supports options equivalent to:

  * `include_headers`
  * `include_footers`
  * `include_footnotes`
  * `include_watermarks`
  * `strip_repeating_text`
* what their current/default values are
* whether our current integration explicitly configures them or simply inherits defaults

Report exact source locations/API definitions supporting the conclusions.

Create a small result matrix for every known target string.

* moved to an unexpected location

## 5. Determine where information is actually lost

For each engine distinguish between these failure modes:

### Extraction loss

The text/reference is absent from the engine's document model entirely.

### Classification loss

The text exists, but is classified as header/footer/furniture or another non-body category.

### Projection/export loss

The engine retained the text, but our current Markdown/text projection omits it.

### Reading-order degradation

The text exists but becomes difficult to interpret because its order or association with labels is damaged.

### OCR/text-layer problem

The source itself or OCR stage failed to recover the reference reliably.

This distinction is the primary purpose of the investigation.

## 6. Architectural conclusion

Based strictly on the evidence, answer:

1. Is Docling actually losing the important header information, or are we dropping it during projection?
2. Is Xberg actually losing it, or are its default content filters excluding it?
3. Can the problem be solved by changing how we preserve/project existing extractor output?
4. Would a literal text projection still provide independent value?
5. Is `pdftotext -layout` justified as a future narrow `plain_text_projection` / fallback processor?
6. Or would adding it now merely duplicate information already available from Docling/Xberg?

Do not implement the resulting recommendation yet.

## Important architectural constraint

Do not assume that "page furniture" means semantically unimportant content.

For this corpus, headers and footers may contain some of the most legally important metadata in the document.

At the same time, do not simply concatenate furniture into canonical body Markdown without considering provenance.

A likely future model may distinguish:

```
structured document
    BODY
    FURNITURE
```

from a derived:

```
full_text / search_text
```

containing both.

This investigation should determine whether that direction is supported by actual extractor behavior.
