# Objective

Implement the **smallest PDF evidence-extraction slice** justified by the completed C5.3 findings.

Do not reopen the broad investigation.

Do not redesign the processing model.

Do not replace Docling or Xberg.

Do not implement generalized PDF forensics.

The goal is to reduce proven silent evidence loss by adding a small set of durable, provenance-aware evidence artifacts derived directly from the immutable source PDF binary.

The implementation baseline established by C5.3 is:

* the original `file_binary` PDF remains the authoritative evidence source;
* Docling and Xberg remain downstream interpretation engines, not the primary PDF evidence boundary;
* different PDF evidence channels must remain distinguishable;
* a useful first slice should focus on:
  * literal PDF text;
  * signature metadata;
  * compact PDF structure inventory;
  * conditional OCR text.

---

# Context

The completed C5.3 investigation established several repository-specific facts:

1. interpretation-engine text is not a complete inventory of PDF evidence;
2. signed PDFs are common in the retained corpus;
3. image-only and mostly-image PDFs are common enough to justify a distinct OCR evidence channel;
4. low-level PDF tooling exposes evidence channels that Docling/Xberg do not;
5. the regression case
   `6836f8732aae33a3bc79491748134bd2a77a7b48aeaa2cd7c66647ff1f468f1c`
   proves that visible signature-appearance text can exist in the PDF and be recoverable by `pdftotext` while remaining absent from Docling/Xberg text output.

The next step is therefore not another projection tweak.

It is the first durable evidence-artifact slice.

---

# Architectural boundary

Preserve the distinction:

```text
immutable PDF binary
    -> PDF evidence artifacts
    -> interpretation artifacts
```

Evidence artifacts answer:

> What evidence-bearing information can we extract directly from this PDF binary?

Interpretation artifacts answer:

> How should humans or downstream systems read and use this document?

Do not collapse these concerns.

In particular:

* do not treat `pdf-literal-text` as equivalent to Docling/Xberg text;
* do not treat OCR text as equivalent to native PDF text;
* do not treat visible signature text as equivalent to cryptographic signature metadata;
* do not treat signature extraction as legal validation.

---

# Scope

Implement only the first bounded evidence-artifact slice recommended by C5.3.

## In scope

### 1. `pdf-literal-text`

Persist a durable artifact representing recoverable low-level PDF text.

Intended semantics:

* channel-specific artifact
* derived from the source PDF directly
* not authoritative reading order
* not semantic structure
* not a replacement for Docling/Xberg text
* an empty result means the selected literal-text extractor produced no literal text under that profile; it does not prove that no textual evidence exists elsewhere in the PDF

Requirements:

* use a low-level PDF text extractor appropriate to the current repository environment
* preserve clear provenance:
  * tool identity
  * tool version where practical
  * mode/configuration
* define the exact extraction mode used
* keep the artifact name explicit and channel-specific
* do not reuse or silently redefine existing `text.txt` / `complete-text.txt` semantics

This artifact is justified specifically because it can recover visible PDF-layer text omitted by interpretation engines.

### 2. `pdf-signature-metadata`

Persist a durable artifact capturing signature-related evidence when present.

This artifact should preserve signature-structure and certificate facts where practically extractable.

Minimum structural target facts should follow the C5.3 findings where extractable:

* signature field name
* whether the field is populated
* `/ByteRange`
* signing timestamp fields
* signer/name fields
* reason/location/contact fields where present

Certificate enrichment may include, where practical without broadening the phase:

* certificate subject
* certificate issuer
* certificate serial/fingerprint

Preserve provenance of which extractor/tool produced the facts.

Keep separate:

* visible signature appearance text
* signature/form structure
* certificate/signature metadata

Do not implement or imply:

* cryptographic validation
* trust-chain validation
* revocation status checking
* legal validity analysis

### 3. `pdf-structure-inventory`

Persist a small, explicit inventory of which evidence-bearing channels the PDF contains.

The inventory should stay compact and implementation-driven.

At minimum it should be able to record whether the PDF appears to contain:

* native text
* page-raster/image content
* annotations
* widgets / AcroForm
* signature fields / signature dictionaries
* embedded-file indicators where detectable

This is not a giant forensic dump.

Its purpose is to reduce silent assumptions about channel absence.

Where a channel is not actually inspected or the selected extractor cannot determine it reliably, the inventory must distinguish:

* present
* absent
* unknown

Do not collapse "not inspected" or "not exposed by this extractor" into `false`.

### 4. Conditional `ocr-text`

Persist OCR-derived text only for PDFs where OCR is actually the relevant evidence channel.

Use the existing readability classification as the initial OCR-selection mechanism.

Expected scope:

* `image_only_pdf`
* `mostly_image_pdf`
* selected `mixed_pdf` only if a narrower explicit rule is defined and validated during implementation

Requirements:

* OCR text must remain explicitly distinct from native PDF text
* OCR provenance must be explicit:
  * engine/tool
  * version where practical
  * configuration/profile
* do not introduce a generalized text-strength or OCR heuristic in this slice
* do not rewrite the authoritative PDF
* do not create an OCR-enhanced replacement PDF and treat it as evidence-equivalent to the original

### 5. Evidence-artifact provenance

Every new artifact introduced in this slice must remain attributable to:

* source binary SHA-256
* extractor/tool identity
* extractor/tool version where practical
* configuration/profile/mode
* generation timestamp if consistent with the repository model

Use the existing processing/representation model where practical.

Prefer additive, narrow integration rather than introducing a new parallel provenance framework unless the current model genuinely blocks correct implementation.

# Specific regression requirement

The implementation must explicitly validate the known regression case:

`6836f8732aae33a3bc79491748134bd2a77a7b48aeaa2cd7c66647ff1f468f1c`

Expected evidence behavior:

* literal PDF text extraction must preserve the visible signature text beginning with:
  `Assinado em 13-01-2022, por`
* signature metadata extraction must preserve the structural signature evidence for the PDF
* Docling/Xberg outputs may continue to omit that visible signature text in their own interpretation artifacts
* the system must preserve the distinction rather than forcing agreement

Do not special-case the code around this single file.

Use it as a must-pass regression example for the general mechanism.

# Tooling/runtime policy

Follow the C5.3 findings.

The implementation may use the most practical local tooling available, including:

* current Windows-local tooling
* current repository runtime
* existing local CLI tools

Linux/WSL/containerized low-level PDF tooling remains a valid operational option, but C5.3 did **not** justify making it the main scope of this slice.

Therefore:

* do not broaden this phase into a Linux tooling investigation;
* do not build a Docker service;
* do not redesign the worker around container orchestration;
* do not block the implementation merely because some future Linux-only tooling might be nicer.

If one narrow Linux/WSL/containerized probe is genuinely required for a specific evidence channel and materially improves correctness, document it explicitly and keep the usage minimal.

---

# Integration expectations

Preserve the existing processing execution model.

Do not introduce new scheduling, queue, worker, or orchestration infrastructure as part of this slice.

The intended direction is:

```text
file_binary
    -> evidence-oriented processing
    -> durable PDF evidence artifacts

file_binary
    -> Docling / Xberg interpretation
```

Do not contaminate canonical domain tables with processor-specific evidence columns.

Do not introduce:

* `document.extracted_text`
* `document.signature_status`
* `document.pdf_text`
* `document.ocr_text`

Selection and consultation behavior can remain separate concerns.

This phase is about durable evidence extraction, not final UI presentation policy.

---

# Required design discipline

Prefer the smallest implementation that materially reduces silent evidence loss.

The default first-slice priorities are:

1. literal PDF text
2. signature metadata
3. compact structure inventory
4. OCR text where actually needed

Do not turn the slice into a generalized PDF schema merely because more channels exist.

Do not persist every diagnostic just because a tool can emit it.

Persist only what is justified as a durable evidence artifact.

---

# Explicitly deferred work

Do not implement in C5.3.1:

* generalized annotation-content extraction beyond what is strictly required for the selected artifact semantics
* embedded-file extraction if the slice can succeed with structural inventory only
* full revision-chain / incremental-signature persistence
* full certificate trust-chain validation
* revocation checking
* legal signature validity
* search-text aggregation
* semantic/legal extraction
* taxonomy
* summarization
* representation-selection redesign
* Docling/Xberg replacement
* new viewer/UI work
* container orchestration
* large schema redesign
* remote storage work

If the implementation discovers that one of these items is actually required for correctness, stop and document the reason before broadening scope.

# Constraints

Do not:

* reopen the broad C5.3 investigation;
* redesign the processing model unless a real blocker is found;
* silently redefine existing artifacts;
* treat any one text output as universally authoritative;
* merge native PDF text, OCR text, and signature metadata into one undifferentiated artifact;
* mutate the authoritative source PDF;
* implement legal or semantic interpretation;
* add large dependencies without a clear need;
* implement generalized PDF forensics;
* broaden into Phase D or later work.

Keep the slice narrow, evidence-oriented, and reproducible.
