# Phase C4 Consultation MVP Inspection Note

Last updated: 2026-08-31

## Purpose

Define the smallest practical implementation of `C4 - Corpus Consultation MVP` after completion of Phases C1-C3.2.

This note is repository-grounded. It does not reopen the accepted roadmap. It records what already exists, what can already be shown, and the smallest clean implementation boundary for the first consultation UI.

## Repository Findings

### Directus state

- `docker-compose.yml` already defines a runnable `directus/directus:11.5.1` service on `http://localhost:8055`
- Directus is configured against the same PostgreSQL database as the rest of the repository
- the live local stack currently has `virgilio-case-directus`, `virgilio-case-db`, and `virgilio-case-gateway` running
- no Directus custom extensions are present under `app/extensions`

Directus is therefore already a real raw/admin consultation surface, not just a future idea.

### Current HTTP/API surfaces

- the only repository-owned HTTP server is `app/file-gateway.mjs`
- it is exposed by `package.json` as `start:gateway`
- it serves original binaries by SHA-256 at `/binary/<sha256>`
- it now resolves canonical binaries through `BinaryStore -> LocalBinaryStore`
- there is no existing structured Virgilio consultation API
- there is no existing API framework, router, or frontend server beyond Directus and the file gateway

### Current frontend state

- no React frontend exists
- no TypeScript frontend exists
- no Vite, Next, MUI, or PDF.js integration exists yet
- there is no `ui/`, `web/`, `frontend/`, or `client/` application to extend
- `package.json` currently contains backend/import/processing scripts only

The consultation UI therefore needs a new client rather than an extension of an existing one.

## Existing admin/read surfaces

### Directus-readable canonical views

The repository already has these consultation views in PostgreSQL:

- `casework.v_case_summary`
- `casework.v_bucket_summary`
- `casework.v_document_summary`
- `casework.v_unresolved_document`

These are useful for raw/admin consultation and remain better suited to Directus than exposing only normalized tables.

### Directus-visible processing tables

The current schema also contains the relevant processing tables:

- `casework.processing_job`
- `casework.document_representation`
- `casework.document_segment`
- `casework.document_representation_selection`
- `casework.document_representation_comparison`

Directus is already sufficient for read-first raw/admin inspection of both canonical and processing state without additional Directus development.

It is not sufficient by itself for the desired C4 human-facing binary catalogue/detail experience, because that experience needs curated aggregate/read models and reuse of existing selection/comparison logic.

`document_representation` currently persists:

- `representation_source_kind`
- `representation_variant_key`
- `representation_kind`
- `format_family`
- `processor_key`
- `processor_version`
- `based_on_representation_id`
- `metadata_json`
- `content_json`
- `artifact_rel_path`
- `produced_by_job_id`
- timestamps

`document_segment` currently persists:

- full extracted text in `text_content`
- segment ordering
- optional structural/page/character fields
- `metadata_json`

### Current live representation inventory

Live local data currently contains:

- `21` `document_representation` rows
- `21` `document_segment` rows
- `0` explicit `document_representation_selection` rows
- `3` `document_representation_comparison` rows

Current live source-kind and processor breakdown:

- `11` machine-generated `docling` representations
- `10` machine-generated `xberg` representations
- `0` persisted human-authored representations in the live DB
- `0` persisted plain-text passthrough representations in the live DB

### What Docling currently persists

Docling representations currently retain:

- compact representation summary in `content_json`
- processor/profile/OCR/native-summary metadata in `metadata_json`
- full extracted plain text in `document_segment.text_content`
- `artifact_rel_path` pointing at an output directory
- on-disk artifacts:
  - `text.txt`
  - `markdown.md`
  - `native.json`
  - `summary.json`

Docling Markdown is therefore actually retained today, but on disk under `artifact_rel_path`, not duplicated into PostgreSQL.

### What Xberg currently persists

Xberg representations currently retain:

- compact representation summary in `content_json`
- processor/profile/OCR/native-summary metadata in `metadata_json`
- full extracted plain text in `document_segment.text_content`
- `artifact_rel_path` pointing at an output directory
- on-disk artifacts:
  - `text.txt`
  - `native.json`
  - `summary.json`

Xberg Markdown is not currently retained because Xberg does not currently emit a Markdown artifact in this repository.

### Human and plain-text representations

The runtime already supports:

- human-authored representations through `createHumanRepresentation(...)`
- plain-text passthrough processing through the processor registry

However, the current live DB does not yet contain rows for either of those paths.

### Artifact retrieval boundary

There is currently no HTTP runtime boundary for representation artifacts.

`artifact_rel_path` is currently a filesystem-relative reference used by processing/runtime and evaluation tooling. It is not yet exposed by a gateway/API suitable for the consultation UI.

### Segment granularity

The current live DB has `21` segments for `21` representations:

- one segment per representation
- `page_no` is currently null on all live rows
- `structural_path` is currently null on all live rows

That means C4 can reliably show full text immediately, but should not promise page-aware text navigation or structure-aware browsing yet.

## Effective-selection, comparison, and attention logic

The existing backend already has reusable logic in `app/processing-store.mjs` for:

- `listRepresentationsForBinary(...)`
- `resolveEffectiveRepresentation(...)`
- `listComparisonsForBinary(...)`
- `deriveRepresentationAttention(...)`
- `inspectRepresentationState(...)`
- `inspectJobs(...)`
- `countProcessingState(...)`

This logic is already implemented server-side in JavaScript. The frontend should not reimplement it.

Current semantics already support:

- automatic effective-selection policy
- explicit selection override when one exists
- comparison visibility
- review-needed/attention derivation

Current live state has no explicit selection overrides yet, but the infrastructure is already in place.

## Binary-to-document context findings

`file_binary` does not map one-to-one to logical documents.

Live local data currently shows:

- `1222` binaries linked to exactly one canonical document
- `16` binaries linked to more than one canonical document
- `5` binaries linked to multiple distinct document names
- maximum observed multiplicity:
  - `3` documents
  - `15` buckets
  - `4` cases

So the C4 UI must not assume:

- one binary = one document
- one binary = one case

### Recommended human display label

For the binary catalogue:

- if exactly one linked document exists:
  - use that document name as the primary label
- if multiple linked documents exist but share one name:
  - use that shared name plus a multiplicity badge
- if multiple linked documents have different names:
  - use a compact synthesized label such as `Multiple linked documents`
  - show the first few names in secondary text or detail hover
- if names are sparse:
  - fall back to SHA prefix plus type/size and case context

The detail page should show the full linked-document list explicitly rather than trying to compress multiplicity away.

## PDF and representation rendering feasibility

### Original PDF serving

The existing `/binary/<sha256>` gateway already provides:

- correct `Content-Type`
- `Content-Length`
- `Content-Disposition: inline`
- `HEAD` support
- SHA-based lookup
- safe binary-store-backed file retrieval

That is sufficient for the first MVP.

### Range requests

The current gateway does not implement HTTP range requests.

For the current local MVP and modest corpus, full-file streaming is acceptable. Lack of range support may reduce PDF.js performance on larger files, but it is not a blocker for the first C4 slice.

If the first UI integration shows a real usability issue, range support can be treated as a small later C4 refinement rather than a prerequisite.

### CORS / origin shape

If the new frontend runs on a different dev port from the gateway, the project should prefer a local dev proxy or same-origin deployment shape rather than expanding gateway behavior immediately.

This avoids introducing CORS work as part of the first thin consultation slice.

### Representation rendering

Immediately feasible rendering modes are:

- Docling text:
  - from `document_segment.text_content`
- Docling Markdown:
  - from `artifact_rel_path/markdown.md`
- Docling native JSON:
  - from `artifact_rel_path/native.json`
- Xberg text:
  - from `document_segment.text_content`
- Xberg native JSON:
  - from `artifact_rel_path/native.json`
- Human text:
  - from `document_segment.text_content` once such rows exist

Recommended MVP rendering:

- Markdown:
  - rendered Markdown plus optional raw toggle
- text:
  - preformatted text viewer
- JSON:
  - formatted/collapsible JSON viewer without building a complex editor

## Recommended C4 data-access architecture

### Options considered

`Option A`

```text
React
  -> Directus API for structured data
  -> file-gateway for original binary
```

This is not recommended as the main C4 implementation path because it would either:

- push effective-selection/comparison/attention aggregation into the frontend, or
- force awkward overloading of Directus for Virgilio-specific read models

`Option B`

```text
React
  -> small Virgilio consultation API
  -> PostgreSQL/read helpers
  -> file-gateway for original binary
```

This is the recommended C4 path.

It is the smallest option that:

- keeps human-oriented aggregation server-side
- reuses the existing selection/comparison logic
- avoids coupling the human-facing UI to Directus
- stays aligned with later search-result and AI-citation navigation

`Option C`

```text
React
  -> small consultation API
       -> Directus where useful
       -> file-gateway
```

This adds complexity without clear value for the first MVP.

### Recommendation

Use:

```text
React client
  -> small Virgilio consultation API
  -> file-gateway for original binary

Directus
  -> remains raw/admin consultation surface
```

The consultation API should own:

- binary catalogue read model
- binary detail read model
- representation/selection/comparison/attention reuse
- safe representation artifact reads needed for Markdown/JSON/text viewing

## Recommended frontend stack

Because no frontend already exists, the smallest clean UI direction is:

- React
- TypeScript
- Vite
- MUI or similarly mature component library
- PDF.js for original PDF viewing

This remains a recommendation, not an implemented dependency set.

## Proposed binary catalogue read model

The catalogue should be binary-oriented, not a raw `file_binary` table dump.

Minimum row:

- `file_binary_id`
- `sha256`
- `display_name`
- `mime_type`
- `file_extension`
- `size_bytes`
- `document_count`
- `bucket_count`
- `case_count`
- `linked_document_names`
- `linked_case_refs`
- `processing_summary`
- `available_representations`
- `effective_representation`
- `effective_selection_reason`
- `review_needed`
- `review_reason_codes`
- `last_processed_at`

### Cheap versus heavier fields

Cheap enough for query-time derivation:

- binary identity/type/size
- document/bucket/case counts
- linked-document names
- linked-case references
- available representation list
- latest processing timestamps

Prefer backend helper composition rather than frontend recomputation for:

- effective representation
- effective selection reason
- review-needed state
- comparison summary

If catalogue queries become awkward, a small SQL view may later be justified, but no schema change is needed for the first slice.

## Proposed binary detail read model

The detail page should expose:

- `binary`
  - `file_binary_id`
  - `sha256`
  - type/size/readability metadata
- `context`
  - linked documents
  - linked buckets
  - linked cases/workspaces where determinable
  - primary/non-primary document-binary information
- `processing`
  - processing jobs
  - status history as currently persisted
  - recent failures
  - timestamps
- `representations`
  - all available representations
  - available view formats per representation
  - effective representation
  - explicit selection if any
  - automatic selection reason
- `comparison`
  - current comparison summaries
  - disagreement level
- `attention`
  - review-needed boolean
  - machine-readable reason list
- `provenance`
  - representation source kind
  - processor
  - processor version
  - produced-by job
  - created_at
  - based_on_representation_id
- `technical_details`
  - internal IDs
  - raw metadata JSON
  - raw content summary JSON
  - artifact paths

The upper visual layout can remain:

- left: original PDF
- right: selected representation view

The lower section should summarize context, processing, provenance, and attention in human-readable form.

## Proposed pages and identifiers

Recommended first routes:

- `/binaries`
- `/binaries/:sha256`

Use `sha256` as the main route identifier.

Why:

- it is already the stable binary identity used by the file gateway
- it travels cleanly into later citations and download/open-original actions
- it avoids presenting internal integer IDs as the public navigation key

The structured consultation API can still resolve the numeric `file_binary.id` internally and return it in payloads.

## Explicit MVP exclusions

Do not include in the first C4 implementation:

- editing canonical metadata
- manual representation authoring
- representation preference editing unless it becomes almost free after the read API exists
- annotations
- PDF/text synchronization
- bounding-box overlays
- semantic metadata editing
- timeline or graph views
- work-group workflow
- search
- AI chat
- authentication/authorization redesign
- public-deployment concerns

## Recommended implementation slicing

Split C4 into two explicit checkpoints.

### C4.1 Consultation backend/read models

Implement:

- a tiny consultation API in `app/`
- binary catalogue endpoint
- binary detail endpoint
- representation artifact read endpoints needed for Markdown/JSON/text viewing
- reuse of existing selection/comparison/attention logic in `processing-store`

Do not implement the React UI in this slice.

### C4.2 Consultation UI

Implement:

- React/Vite client
- binary catalogue page
- binary detail page
- PDF.js original-binary panel
- representation selector and viewer
- human-readable processing/provenance/attention panels

This split is justified because there is currently:

- no frontend
- no structured consultation API
- already useful backend logic worth exposing cleanly before UI work

It also gives a clean rollback point before the visual/UI layer.

## Reusable boundaries for later Phase D

The recommended C4 shape is not throwaway.

Reusable later:

- `/binaries/:sha256` as the destination for search results and AI citations
- representation detail payloads as the basis for search-result provenance
- server-side effective-selection resolution for later retrieval
- the file gateway as the original-binary citation/open boundary

This keeps later navigation coherent:

```text
search result
  ->
binary detail
  ->
representation detail
  ->
original binary by sha256
```

## Recommended next implementation prompt

The first implementation slice should be `C4.1 consultation backend/read models`.

Suggested scope:

1. inspect the current `processing-store` and `file-gateway` boundaries and preserve them
2. add a small read-only consultation API in `app/` without changing schema, importer, or processing behavior
3. expose:
   - binary catalogue read model
   - binary detail read model
   - safe representation-content endpoints for text/Markdown/native JSON
4. keep Directus unchanged as raw/admin consultation
5. keep original-binary serving on the existing `/binary/<sha256>` gateway path
6. do not implement React/Vite/PDF.js yet
7. do not start Phase D search or semantic enrichment

The main boundary should be:

```text
custom consultation UI
  ->
consultation API
  ->
processing/canonical read helpers

original binary
  ->
file-gateway
  ->
BinaryStore
```
