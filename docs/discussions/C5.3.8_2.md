# C5.3.8 Result — Portable Evidence Package First Vertical Slice

## Outcome

C5.3.8 implemented the first bounded portable export slice for one selected `file_binary`.

The exported package is a self-contained directory with:

* one machine-readable `manifest.json`;
* the exact original binary copied through `BinaryStore`;
* persisted canonical/procedural context for that binary;
* persisted `processing_job` history for that binary;
* all persisted reachable `document_representation` rows for that binary;
* copied persisted representation artifact directories;
* derived convenience metadata kept explicitly separate from persisted state.

No schema, bootstrap, importer, processor, or consultation-route changes were required.

## Exporter entry point

The implementation uses:

* exporter module: `app/portable-export.mjs`
* admin/CLI entry point: `node app/processing-admin.mjs export-binary --sha <sha256> --output <directory>`

This keeps the export slice inside the existing processing administration boundary rather than introducing a separate export subsystem.

## Selection mechanism

The current entry point selects the export root binary by canonical SHA-256:

```text
--sha <file_binary.sha256>
```

The representative live validation binary remained:

```text
6836f8732aae33a3bc79491748134bd2a77a7b48aeaa2cd7c66647ff1f468f1c
```

## Output-directory policy

The exporter requires the target output directory not to exist.

It does not merge into an existing directory.

If export fails after directory creation, the partial package directory is removed.

## Actual package structure

The implemented package shape is:

```text
<export-root>/
  manifest.json
  originals/
    <sha256><extension>
  representations/
    <representation-id>/
      artifacts/
        ...
```

The manifest always uses package-relative paths.

## Manifest top-level structure

The top-level shape is:

```json
{
  "package_format": "virgilio-portable-evidence",
  "package_version": 1,
  "exported_at": "...",
  "persisted": { ... },
  "package_contents": { ... },
  "derived": { ... }
}
```

This keeps three categories explicit:

1. persisted repository state;
2. package-local copied content;
3. exporter-derived convenience information.

## Package format/version

Implemented:

* `package_format = "virgilio-portable-evidence"`
* `package_version = 1`

This is a repository-internal C5.3.8 package contract, not a general interoperability standard.

## Canonical identity rule

Portable identity is based on persisted canonical binary identity:

```text
file_binary.sha256
```

Source storage metadata such as:

* `storage_package_id`
* `storage_rel_path`

is retained only as provenance/debug metadata under the persisted `file_binary` record.

The package itself is interpreted through package-relative copied content.

## Original-binary retrieval and SHA validation

The original binary is retrieved through `LocalBinaryStore`/`BinaryStore` materialization rather than direct filesystem reconstruction inside the exporter.

The exporter then:

1. copies the materialized binary into `originals/<sha256><extension>`;
2. re-hashes the copied file;
3. rejects the export if the copied SHA-256 does not match `file_binary.sha256`;
4. rejects the export if persisted `actual_size_bytes` is present and the copied size does not match.

## Canonical provenance included

For the selected binary, the package currently includes persisted rows for:

* `file_binary`
* `import_batch` resolved through `storage_package_id`
* `document_binary`
* `document`
* `bucket_document`
* `bucket`

Empty relationship sets remain honestly empty.

The representative binary had no `document_origin` rows, and the package preserved that fact rather than inventing one.

## Processing-job history included

The package includes all persisted `processing_job` rows for the selected `file_binary`, ordered deterministically by `requested_at, id`.

Included fields cover:

* `id`
* `stage_key`
* `status`
* processor identity/version
* timestamps
* `attempt_count`
* `max_attempts`
* `error_code`
* `error_text`
* `depends_on_job_id`
* produced-representation relationship resolved from persisted `document_representation.produced_by_job_id`

The representative package preserved both failed and successful historical rows.

## Representation metadata included

The package includes all persisted representations reachable through the current DB/artifact model for the selected binary, not just the current preferred interpretation.

Each exported representation records:

* representation identity;
* representation kind;
* processor identity/version;
* representation source kind;
* variant/based-on provenance where present;
* persisted `metadata_json` and `content_json`;
* persisted `artifact_rel_path`;
* ordered persisted segments.

## Artifact handling

If a representation has a persisted `artifact_rel_path`, the exporter:

1. resolves that path through the existing artifact-resolution boundary;
2. enumerates the files currently present under that persisted artifact directory;
3. copies that directory into `representations/<representation-id>/artifacts/`;
4. records both source artifact metadata and copied package-relative file metadata in `package_contents.representation_artifacts`.

The exporter does not create new artifacts during export.

It copies only persisted reachable artifact directories.

## Segment handling

Persisted `document_segment` rows are included inside each exported representation in deterministic sequence order.

No additional large synthetic text artifact is created from segments during export.

## Selection/comparison handling

Where present, the package includes persisted:

* `document_representation_selection` rows;
* `document_representation_comparison` rows.

The package also includes one explicitly derived convenience summary:

```text
derived.effective_selection
```

This remains separate from persisted selection rows.

## Persisted versus derived information included

Persisted sections are under:

* `persisted`

Copied package-local content is under:

* `package_contents`

Derived export-time convenience information is currently limited to:

* `derived.effective_selection`

No derived rollout/applicability summary was added in C5.3.8.

## Partial-processing behavior

The exporter accepts partially processed binaries.

The representative validation binary included:

* historical failed processing jobs;
* successful interpretation representations;
* successful PDF evidence representations;
* multiple processor versions;
* no explicit selection override.

That mixed state exported successfully.

The exporter also accepts an imported but unprocessed binary and preserves an honestly empty processing/representation set.

## Deterministic ordering/naming rules

The implemented package uses:

* stable array ordering for persisted rows;
* stable original filename shape based on `<sha256><extension>`;
* stable representation artifact directories based on `<representation-id>`.

`exported_at` is intentionally volatile and therefore the manifest is not required to be byte-identical across repeated exports.

## Read-only guarantees

Export is read-only with respect to repository state.

It does not:

* enqueue jobs;
* run processors;
* create representations;
* create segments;
* create comparisons;
* change selections;
* update existing rows.

Focused tests verified that processing/representation counts remain unchanged before and after both rich and unprocessed export runs.

* archive/ZIP packaging;

* a small case/workspace export root; or
* a consumption-side reader/inspection path for the exported package.

Do not broaden directly into re-import, corpus-wide export, or Phase D from this checkpoint.
