# Phase C5.3.7 — Corpus Processing and Portable Export Readiness Assessment

Implement Phase C5.3.7 as the next narrow checkpoint after the completed C5.3.6 read-only PDF evidence inspection work.

Follow the repository-root `AGENTS.md`.

This is primarily an inspection, assessment, and narrow readiness-hardening phase.

Do not start a full-corpus processing rollout.

Do not start Phase D.

Do not add search, embeddings, semantic enrichment, legal extraction, or AI answering.

Do not add new evidence channels.

Do not redesign canonical/domain/importer semantics.

Preserve unrelated working-tree state, including any pre-existing `package.json` or `tmp/` changes.

## Context

The repository now has the major boundaries needed for persisted PDF evidence:

```text
canonical import / original binaries
        ↓
processing
        ↓
PDF evidence + interpretation representations
        ↓
read-only inspection
```

C5.3.6 established that already-persisted evidence and interpretation outputs can be inspected without triggering processing.

The next question is operational:

> After a full corpus import, can Virgilio safely and incrementally process the imported material later, know what has and has not been processed, resume after interruption/failure, and eventually export the accumulated material together with its metadata and provenance?

This phase should answer that question from the actual repository and database model.

Do not assume the answer.

Inspect and prove it.

## Objective

Establish the readiness of the current architecture for this intended lifecycle:

```text
full import
    ↓
canonical binaries/documents/provenance persisted
    ↓
processing scheduled later
    ↓
evidence + interpretation outputs accumulated incrementally
    ↓
processing can stop/resume safely
    ↓
coverage/completeness can be inspected
    ↓
originals + metadata + provenance + derived outputs
can eventually be exported as a coherent package
```

The primary deliverable is a concrete repository-grounded assessment and, only where clearly necessary, small readiness corrections.

This phase is not the full rollout and is not yet the portable-export implementation.

## Persistence versus derived assessment

For coverage, resumability, and export-readiness analysis, distinguish explicitly between:

* directly persisted current state;
* repository-grounded derived assessment;
* future capability that is not yet implemented.

Do not describe a derived operational conclusion as if it were a first-class persisted model feature.

## Core architectural boundary

Preserve:

```text
IMPORT
    = preserve source material and canonical provenance

PROCESSING
    = derive evidence and interpretations

CONSULTATION
    = inspect already-persisted material

EXPORT
    = package persisted material without changing its meaning
```

Do not make successful extraction a prerequisite for canonical import.

A binary/document should be able to exist canonically even when:

* processing has not yet run;
* some processors are not applicable;
* a processor failed;
* a processor timed out;
* OCR was not required;
* processing is deliberately deferred.

Do not couple importer success to Docling, Xberg, OCR, or PDF evidence extraction.

## Important constraint: export is not implementation scope

Do not implement the final portable-export feature in this phase.

Instead, inspect whether the current persisted model contains enough information to support one later.

The intended future export concept is approximately:

```text
package/
    manifest
    originals/
    representations/
    artifacts/
```

where the manifest can preserve relationships among:

* original binaries;
* SHA/content identity;
* documents;
* buckets/procedural occurrences;
* cases/workspaces where applicable;
* source/provenance;
* `processing_job` rows;
* persisted retry/failure history represented by those rows and their existing semantics;
* representations;
* evidence representations;
* artifacts;
* processor/version identity;
* selection information;
* comparison information where applicable.

Do not treat this directory shape as a required implementation design.

The point of this phase is to verify whether the underlying persisted identities and relationships are sufficient to support such an export later.

## Required inspection — import boundary

Inspect the current importer and canonical persistence model.

Report:

1. what constitutes successful import today;
2. whether original binaries remain available for later processing;
3. how `file_binary` content identity is preserved;
4. how documents resolve to binaries;
5. how bucket/document/procedural provenance is preserved;
6. whether processing is already independent of importer execution;
7. whether anything currently requires processing to happen during import;
8. whether a fully imported but completely unprocessed binary is a valid repository state.

Do not modify importer behavior unless inspection finds a concrete blocker to later processing.

If no blocker exists, leave the importer unchanged.

## Required inspection — post-import processing

Determine exactly how an already-imported binary becomes eligible for later processing.

Trace:

```text
persisted binary
    ↓
eligibility/applicability
    ↓
job enqueue
    ↓
worker claim
    ↓
processor execution
    ↓
representation/artifact persistence
```

Report the relevant code paths.

Determine whether processing can already be initiated independently of import for an arbitrary existing eligible binary.

Do not run a full-corpus processing operation merely to answer this.

## Required inspection — processing coverage

Determine whether the current persisted state can answer, for each eligible binary and processor:

```text
not evaluated / not scheduled
queued
running
completed
failed
timed out
not applicable
superseded / older processor identity
```

Use the repository's actual semantics rather than forcing these exact labels if the model differs.

These proposed labels are analytical questions, not assumed schema/state-machine values.

Inspect and report:

* which states are persisted directly;
* which can be derived reliably from existing persisted state;
* which would require additional implementation.

The important requirement is to determine whether Virgilio can distinguish:

```text
we have not processed this
```

from:

```text
we processed this successfully
```

from:

```text
we attempted this and it failed
```

from:

```text
this processor does not apply
```

where applicable.

Identify any ambiguity.

Do not invent new state solely to make a prettier coverage report.

## Required inspection — resumability

Determine whether a future large processing rollout can safely stop and resume.

Inspect:

* job identity/deduplication;
* representation identity;
* completed-job handling;
* failed-attempt history;
* persisted timeout-related status/error/timestamp history;
* retry behavior;
* current heavy-processing concurrency;
* processor applicability/gating;
* behavior after worker restart;
* behavior when processing is interrupted.

Use repository-accurate terminology.

Describe the actual persisted `processing_job` rows, retries, failures, and produced representations.

Do not imply a separate execution-attempt table or richer attempt-history model unless repository inspection proves that one exists.

Answer explicitly:

> If processing 1,700+ imported files is interrupted halfway through, can the repository determine what work remains without blindly reprocessing everything?

If yes, explain exactly how.

If only partially, identify the precise gap.

Do not implement a new scheduler merely because a future rollout may be large.

## Required inspection — idempotence / duplicate protection

Determine what prevents a future resumed rollout from:

* creating duplicate same-identity successful representations;
* overwriting historical failed attempts;
* overwriting existing successful derived material;
* repeatedly enqueueing already-completed work;
* confusing an old processor/version result with a current one.

Distinguish `processing_job` identity and persisted retry/failure history from representation identity.

Use terminology grounded in the actual `processing_job` and representation model rather than implying a separate execution-attempt schema.

Do not change representation identity semantics unless an actual correctness defect is found.

## Required inspection — processor applicability

Inspect what information exists before expensive processing begins.

For PDFs, determine how the repository currently knows or can derive whether the following are applicable:

* `pdf_literal_text`;
* `pdf_signature_metadata`;
* `pdf_structure_inventory`;
* `pdf_ocr_text`;
* Docling;
* Xberg.

In particular, preserve the existing OCR gating semantics.

Do not make all processors mandatory for all PDFs merely to simplify coverage accounting.

Also note how the current architecture can accommodate non-PDF file types later without making the processing core PDF-specific.

Do not implement DOC/DOCX/spreadsheet processors in this phase.

## Required inspection — full-corpus operational shape

Without running it, determine the smallest safe operational shape for a future full-corpus processing rollout.

Address:

* how eligible binaries would be selected;
* how already-completed work would be skipped;
* how applicable missing work would be identified;
* how jobs would be enqueued;
* whether enqueueing should be bounded/batched;
* how processing could be paused;
* how it could resume;
* how progress could be measured;
* how failures/timeouts would remain visible;
* how heavy concurrency policy would remain respected;
* how completion could be assessed.

Prefer existing mechanisms.

Do not introduce:

* Redis;
* external queues;
* worker frameworks;
* distributed schedulers;
* Kubernetes;
* service mesh.

Do not implement the actual corpus rollout in C5.3.7.

## Required inspection — portable export readiness

Inspect whether the current persisted model can reconstruct the provenance graph needed for a future portable export.

At minimum evaluate whether a future exporter can recover:

### Canonical/source layer

* `file_binary` identity;
* SHA-256;
* MIME/file type;
* original binary content through the storage abstraction;
* document identity;
* document-to-binary relationship;
* bucket/procedural occurrence;
* case/workspace relationships where applicable;
* source/import provenance already persisted.

### Processing layer

* processing job identity and persisted retry/failure history;
* processor key;
* processor/version identity;
* status;
* timestamps;
* timeout/failure identity where persisted;
* relationship between a `processing_job` row and a produced representation.

### Representation layer

* representation id;
* representation kind;
* processor/version provenance;
* source binary/document relationship;
* evidence versus interpretation semantics;
* artifacts belonging to the representation.

### Consultation/derived-policy layer

Where applicable:

* explicit selection records;
* effective-selection-relevant persisted data;
* persisted comparisons.

The future exporter must be able to preserve these relationships without flattening them into a single extracted-text record.

## Export identity rule

Assess whether stable exported references can be based on persisted repository identities plus content identity.

Do not make filesystem/storage paths into portable identity.

In particular:

```text
sha256/content identity
    !=
storage location
```

A future export should remain meaningful if the same package is moved to another machine or storage backend.

Do not change `BinaryStore` merely for export planning.

## Evidence semantics in future export

Verify that the current model can preserve the distinction:

```text
original PDF
    !=
pdf_literal_text
    !=
pdf_ocr_text
    !=
pdf_signature_metadata
    !=
pdf_structure_inventory
    !=
Docling interpretation
    !=
Xberg interpretation
```

A future exporter must not silently convert these into:

```text
document.txt
```

without provenance.

Determine whether the current representation/artifact model already carries enough identity to avoid that loss.

For every material export-readiness finding, distinguish among:

* currently persisted and exportable from existing state;
* inferable or reconstructible from existing persisted state but requiring exporter implementation;
* not currently preserved and therefore requiring a future persistence/model change.

Do not say that information is exportable merely because a future implementation could derive or recreate it.

## Export completeness / partial processing

A future export must be able to represent incomplete processing honestly.

For example, it should be possible to export a binary for which:

```text
original binary       present
literal evidence      present
signature evidence    present
Docling               failed
Xberg                  completed
OCR                    not applicable
```

without treating the package as invalid.

Assess whether the current persisted model can represent this accurately.

## No speculative export schema

* correctly determining processing coverage;

This phase is primarily an assessment/result-note checkpoint.
