## 1. Current import completion semantics

Successful import today means `app/import-package.mjs` can read a valid portable package from `data/imports/<package-id>/`, upsert the canonical package rows into PostgreSQL inside a single transaction, and finish without requiring any processing worker or processor execution.

The importer persists at least:

* `import_batch`
* canonical `case_file`, `bucket`, `document`, `file_binary`, `document_binary`
* workspace links where the schema supports them
* source provenance tables where the schema supports them

It does not enqueue or execute Docling, Xberg, OCR, or PDF evidence extraction as part of import.

## 3. How original binaries remain available for later processing

Original binaries remain available through the canonical `file_binary` row plus the current storage locator:

* `file_binary.storage_package_id`
* `file_binary.storage_rel_path`

`BinaryStore`/`LocalBinaryStore` resolves those fields through `resolveBinaryPath(...)` under `data/imports/`, validates readability and expected size, and materializes a local path for later consumers.

This means import persists enough information for later processing without requiring importer-time extraction.

## 4. Current post-import processing entry point

The current post-import processing path is already independent of import:

```text
existing file_binary
    -> app/processing-admin.mjs enqueue
    -> enqueueJobsForBinary(...)
    -> casework.processing_job
    -> app/processing-worker.mjs / runWorkerLoop(...)
    -> processOneJob(...)
    -> processor execution
    -> document_representation / document_segment / comparisons
```

Relevant repository paths:

* `app/processing-admin.mjs`
* `app/processing-store.mjs`
* `app/processing-worker.mjs`
* `app/processing-registry.mjs`
* `app/binary-store.mjs`

Processing can already be initiated for an arbitrary existing eligible binary by SHA using the admin command path. It is not coupled to the importer lifecycle.

## 6. Current coverage-state model

### Persisted directly

Persisted directly today:

* `processing_job.status`
  * `queued`
  * `running`
  * `completed`
  * `failed`
  * `cancelled`
  * `blocked`
* `processing_job` timestamps and error fields
* successful `document_representation` rows
* `document_segment`
* selection/comparison rows where applicable

### Derived reliably from existing persisted state

Derivable today:

* `not processed yet` for a given processor identity
  * no same-identity successful representation
  * no active same-identity job
* `already satisfied`
  * matching same-identity representation exists
* `timeout-attributed failure`
  * current failed job row plus persisted `error_code` / `error_text` / timestamps
* `not applicable`
  * current binary metadata evaluated against current processor registry
* `older/superseded processor identity`
  * older successful representations/jobs exist but the current processor/version differs

### Not currently preserved as first-class state

Not currently preserved directly:

* explicit `not_applicable` rows
* explicit `not_scheduled` rows
* explicit corpus-rollout membership/progress rows
* a separate execution-attempt history table
* a dedicated timeout-history subsystem

So coverage assessment is possible now, but part of it is derived rather than directly persisted.

## 7. Current resumability behavior

For the current processing model, resumability is mostly already supported.

The important mechanics are:

* active duplicate protection through partial unique indexes on `processing_job`
* successful-output idempotence through same-identity `document_representation` existence checks in `enqueueJobsForBinary(...)`
* abandoned `running` jobs can be requeued by `recoverRunningJobs(...)`
* completed representations are reused rather than duplicated
* historical failed rows can remain while later explicit re-enqueue creates a new queued job row

This means a future larger rollout can stop and resume without blindly reprocessing everything, provided the resume logic evaluates current binaries against:

* current processor applicability policy
* existing successful representations
* existing active jobs
* existing failed rows

That conclusion is a repository-grounded derived assessment, not a first-class persisted rollout-state model.

## 8. Duplicate and idempotence protections

Current protections are concrete and already implemented:

* partial active-job uniqueness on same target/stage/processor/version
* `enqueueJobsForBinary(...)` checks for existing successful same-identity representations before enqueueing
* `enqueueJobsForBinary(...)` checks for existing active same-identity jobs before enqueueing
* `processOneJob(...)` / `markJobCompleted(...)` reuses an existing same-identity representation if one already exists

So resumed processing should not:

* create duplicate same-identity successful representations
* overwrite an existing successful representation
* create duplicate concurrent active jobs for the same identity

## 9. Failed and retry provenance behavior

The repository does not have a separate execution-attempt table.

What it does have is:

* persisted `processing_job` rows
* persisted statuses, timestamps, attempt counts, and error fields
* later explicit re-enqueue that can create a new job row after terminal failure

This supports preserved historical failure rows where the current model uses a new job row for a later retry request.

It does not provide a richer universal attempt-event log beyond those persisted row semantics.

Timeout outcomes are reconstructible only from persisted job/error/timestamp data, not from a separate timeout-history mechanism.

Verified current failed-job snapshot:

* total failed jobs: `13`
* status distribution currently active: `queued=0`, `running=0`
* failed historical rows include:
  * old pre-C5.2/C5.2 Docling/Xberg failures
  * historical `qpdf` warning-exit failures from the already-corrected behavior
  * historical timeout-attributed Docling/OCR failures from the bounded rollout work

## 10. Current heavy-processing constraints relevant to rollout

The worker already distinguishes execution classes and uses current execution policy from `app/processing-registry.mjs`.

Important current behavior:

* cheap evidence processors have higher claim priority
* Docling is `heavy`
* OCR evidence is `very_heavy`
* Docling and OCR share the current heavy concurrency group
* shared heavy group maximum concurrency is `1`
* claim/locking happens in the database
* extraction runs after the claim transaction is released

This is enough for a bounded or larger future rollout without introducing new queue infrastructure.

## 11. Can a future full-corpus rollout safely stop and resume?

Yes, with an important precision:

* `yes` for current processors and current policy as an operational capability built from existing persistence plus current applicability logic;
* `not yes` in the sense of a fully persisted first-class corpus-rollout state machine.

In practical terms, the repository can already determine remaining work for current processor identities by combining:

* `file_binary`
* current processor applicability policy
* existing successful representations
* existing queued/running jobs
* existing failed rows

The main limitation is that some coverage states remain derived rather than explicitly persisted.

## 16. Export-relevant provenance gap

The main export-relevant gap is not missing core provenance.

The main gap is that some operational states would have to be derived at export time rather than read directly from persisted rows:

* applicability
* `not processed yet`
* `not scheduled`
* timeout-attributed categorization
* rollout completeness summaries

That is acceptable for a future exporter if those are treated honestly as derived assessments.

It would be insufficient only if the project later decides those states must themselves be persisted as durable historical facts.

## 17. Filesystem/storage location versus content identity

Yes, the current repository correctly separates content identity from storage location.

Current evidence:

* `file_binary.sha256` is the content identity anchor
* application/runtime retrieval goes through `BinaryStore`
* current local resolution uses `storage_package_id + storage_rel_path`
* artifact reads are based on representation identity plus `artifact_rel_path`

The repository does not treat local filesystem path as canonical evidence identity.

## 18. Partial processing can be represented honestly

Yes.

The current model can already represent a binary where:

* original binary exists canonically
* some evidence representations exist
* some interpretation representations exist
* some processors failed
* some processors have not yet run
* some processors are currently not applicable under the current policy

This is one of the strongest parts of the current model.

It does not require every binary to have one flattened “complete extraction” record.
