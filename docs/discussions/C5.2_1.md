# Phase C5.2 — Preserve Header/Footer Content with Immutable Representation Semantics

C5.1 diagnostic work is complete.

The findings establish that legally important header/footer information is often already recovered by Docling/Xberg but may be classified, filtered, or projected in ways that make it unavailable or less useful.

Implement **Phase C5.2 only**.

Do not start later C5 work or another phase.

---

## 1. Proven C5.1 findings

C5.1 tested:

* Docling `2.123.1`
* Xberg `1.0.14`

The diagnostic established:

### Docling

Virgilio currently writes body-oriented exports using:

* `document.export_to_text()`
* `document.export_to_markdown()`

Docling classifies:

* `PAGE_HEADER` as `ContentLayer.FURNITURE`
* `PAGE_FOOTER` as `ContentLayer.FURNITURE`

A concrete tested PDF proved that important procedural metadata such as:

* `Processo: 13608/14.8T2SNT`
* `Referência: 134937241`
* `Juízo de Família e Menores de Sintra - Juiz 6`

was retained in `FURNITURE`, even though part of it was absent from the current BODY-oriented output.

Therefore the main problem is not primary extraction loss.

It is primarily:

* classification loss
* projection/export loss
* reading-order/prominence degradation

### Xberg

Installed Xberg `1.0.14` exposes `ContentFilterConfig`.

Relevant defaults include:

* `include_headers=False`
* `include_footers=False`
* `strip_repeating_text=True`
* `include_watermarks=False`

Current Virgilio extraction does not explicitly set `content_filter`.

The C5.1 samples did not prove strong Xberg extraction loss, but relying implicitly on these defaults is not an appropriate preservation policy for this legal corpus.

### pdftotext

`pdftotext -layout` remains useful as a literal page-surface baseline and debugging tool.

Do not add it as a production processor in C5.2.

# 2. Critical repository invariant: representation immutability

Before implementation, inspect and preserve the repository's existing `document_representation` semantics.

A successful `document_representation` is a durable extraction result.

Ordinary processing treats an already-successful matching processor/version representation as satisfied.

Therefore:

> **C5.2 must not silently rewrite artifacts belonging to an already-successful persisted representation while keeping the same representation identity.**

Specifically, do not overwrite existing persisted artifacts such as:

* `text.txt`
* `markdown.md`
* `native.json`
* or any other artifact

for an existing successful Docling/Xberg representation merely because extraction/projection policy has changed.

Changing projection/filter policy changes the meaning of the resulting representation.

That change must be visible in representation identity or be performed through an explicit recomputation mechanism.

---

# 3. Decide the refresh identity before changing extraction behavior

Inspect the existing processor/profile/version identity model first.

Determine exactly what fields cause two processing runs to be considered:

* the same representation
* or distinct representations

Then choose the narrowest correct approach.

Preferred approach:

## Option A — New processor/profile/version identity

Treat the C5.2 projection/filter policy change as a new processor/profile/version identity so that new durable representations are created without mutating historical ones.

Use the repository's existing version/profile mechanism if it already supports this cleanly.

This is preferred if possible.

Alternative only if existing architecture clearly supports it better:

## Option B — Explicit recomputation path

Define a narrowly scoped, explicit recomputation path that intentionally produces refreshed output.

If this approach is used, it must be obvious that recomputation is occurring and must not accidentally convert ordinary same-version processing into destructive artifact replacement.

Do not build a general reprocessing framework.

## Prohibited approach

Do not:

1. keep the same durable representation identity,
2. rerun Docling/Xberg under different projection/filter semantics,
3. overwrite the existing successful artifacts.

Before implementation, state which identity/recomputation approach you are using and why it matches current repository semantics.

If neither approach can be implemented safely without a schema or architectural change, stop and report that constraint rather than silently weakening representation immutability.

---

## 4. Representation identity preference

When introducing the C5.2 policy, prefer a new durable representation identity using the repository's existing identity knobs:

* `processor_key`
* `processor_version`
* processing profile/config metadata where that participates in identity

Do **not** change `representation_kind` merely to force a new row unless the new output is genuinely a different semantic representation kind.

The preferred model is:

```
same representation_kind
+ changed processor/profile/version identity
= new immutable representation
```

Only use a different `representation_kind` if repository inspection shows that the new output is semantically distinct enough that this is the correct existing convention.

Document exactly which identity field(s) changed and why.

# 5. Domain preservation invariant

For Virgilio:

> **No extractor-recovered text should be discarded merely because it is classified as page furniture.**

Court headers and footers may contain legally significant:

* proceeding/case references
* filing references
* tribunal/chamber/judge identification
* dates
* lawyer/party information
* registration information
* procedural identifiers

However:

> Preservation does not mean all content belongs in canonical readable Markdown.

Keep preservation and presentation as separate concerns.

---

# 6. Artifact semantics

Current artifact consumption through:

`app/representation-artifacts.mjs`

exposes only the artifact types currently used for:

* Markdown
* native JSON

even though processors may also generate `text.txt`.

Do not assume that an existing text artifact is already a durable, clearly consumable "complete/search projection".

C5.2 must define artifact semantics explicitly.

The desired model is:

### A. Readable body Markdown

Preserve the current role of Markdown as the primarily human-readable/body-oriented projection.

Do not silently redefine it to mean BODY + all FURNITURE.

Existing Markdown semantics should remain as stable as practical.

### B. Complete text projection

Add an explicitly named durable projection whose semantics are:

> Extractor-derived text intended for completeness/search/reference recovery, including both body and page-furniture text where available.

Use a clear artifact name/type consistent with existing repository conventions.

For example, conceptually:

```
complete-text
```

or equivalent repository-native naming.

Do not blindly use this literal name if the repository has an existing artifact naming convention.

The important requirement is that its semantics are explicit and not confused with ordinary body text.

### C. Native representation

Preserve existing native/structured extractor data where already supported.

Where Docling provides BODY/FURNITURE classification and provenance, do not destroy that distinction merely to create the complete-text projection.

---

## 7. Existing `text.txt` semantics must be explicit

Current processors already produce `text.txt`.

C5.2 must make an explicit decision about its semantics rather than allowing them to drift accidentally.

Choose one of these two approaches based on existing repository conventions:

### Option A — Preserve `text.txt` semantics

Keep `text.txt` with its current body-oriented/plain-text meaning for backward compatibility.

Add a distinct artifact for the complete projection, using a clearly named repository-native artifact such as conceptually:

```
complete-text.txt
```

or equivalent.

This is preferred if current consumers already rely on `text.txt` meaning body-oriented text.
It is also the preferred default if repository inspection does not demonstrate that `text.txt` is effectively unused or purely processor-internal.

### Option B — Redefine `text.txt` only for the new C5.2 identity

Allow `text.txt` to represent BODY + FURNITURE under the new C5.2 processor/profile/version identity only.

Historical representations retain their original `text.txt` semantics permanently.

If this option is chosen:

* the semantic change must be documented explicitly;
* consumers must be able to distinguish old from C5.2 representations by representation identity;
* no existing artifact may be rewritten;
* no code may assume that all historical `text.txt` files have the new semantics.

Do not choose implicitly.

Before implementation, state which option is being used and why it best matches current repository semantics.

Current planning bias:

* prefer Option A unless repository inspection proves that `text.txt` is not a meaningful consumer-facing or compatibility-relevant artifact;
* if Option A is chosen, keep `text.txt` semantically stable, add a separate complete-text artifact, expose it explicitly through `representation-artifacts.mjs`, and produce it under a new immutable processor/profile/version identity;
* if Option B is chosen instead, justify it explicitly from repository evidence rather than from conceptual neatness alone.

---

# 8. Artifact consumption

If the new complete-text projection is durable, it must also be inspectable/consumable through the existing representation-artifact access layer where appropriate.

Inspect:

`app/representation-artifacts.mjs`

and the related API/service call path.

Make the smallest compatible change necessary so callers can explicitly request/access the new complete-text artifact.

Do not:

* redesign the representation API
* introduce a generic artifact management framework
* change unrelated UI behavior
* expose every processor-internal file automatically

The objective is simply that the new durable artifact is not written into storage but inaccessible through the normal artifact abstraction.

Preserve existing Markdown and native-JSON behavior.

# 9. Docling implementation

Modify the new C5.2 Docling representation policy so extractor-recovered BODY and FURNITURE content are preserved appropriately.

Use installed Docling APIs.

Do not reimplement Docling layout classification.

## Required outputs

### Readable Markdown

Continue to produce the existing body-readable Markdown projection with semantics as close as practical to current behavior.

Do not add repeated headers/footers indiscriminately to this Markdown.

### Complete text

Produce an explicit complete-text projection containing:

* `ContentLayer.BODY`
* `ContentLayer.FURNITURE`

The purpose is:

* search
* reference recovery
* diagnostics
* later metadata extraction

Completeness and deterministic behavior matter more than presentation quality.

### BODY/FURNITURE distinction

Where available in existing native structured output, preserve extractor-native distinction and provenance.

The complete-text projection may flatten content for consumption, but it must not become the only retained representation of layer semantics.

---

# 10. Complete-text ordering

Use Docling's own traversal/ordering facilities where possible.

Do not invent a new semantic reading-order algorithm.

For repeated headers and footers:

* preserve them
* do not deduplicate solely because they repeat
* do not attempt to infer whether repetition is legally meaningful
* do not introduce document-specific cleanup rules

A complete projection may therefore contain repeated page furniture.

That is acceptable in C5.2.

Ranking/deduplication belongs downstream.

---

# 11. Xberg implementation

Make Xberg's preservation policy explicit in the new C5.2 representation identity.

Using only fields confirmed in installed Xberg `1.0.14`, configure the supported equivalents of:

```
include_headers=True
include_footers=True
strip_repeating_text=False
```

For:

```
include_watermarks
```

only enable it if implementation review and C5.1 evidence justify treating watermark-classified text as part of the preservation surface.

Do not reference or attempt to configure unsupported fields such as `include_footnotes` if they are absent in `1.0.14`.

Do not add custom cleanup heuristics.

---

# 12. Xberg artifact semantics

Apply the same explicit artifact-semantic rules to Xberg:

* retain its existing readable representation behavior as much as practical
* ensure preservation-oriented extraction is durably represented
* expose the explicitly named complete-text projection if Xberg can produce one consistently within the current processor architecture

Do not force Docling-specific BODY/FURNITURE semantics onto Xberg if Xberg does not expose equivalent classifications.

The common contract is the semantic purpose of `complete text`, not identical internal extractor models.

---

# 13. Existing representations must remain reproducible as historical outputs

Existing persisted successful representations were generated under earlier processor policy.

Do not retroactively reinterpret their artifact semantics in code in a way that makes old representations appear to contain an artifact they never produced.

For example:

* an old Docling representation must not be reported as having a C5.2 complete-text artifact if none exists
* an old Xberg representation must not be treated as though it used preservation-oriented filters

Consumers must be able to distinguish historical output from C5.2 output through the representation identity/artifact availability already supported by the system.

No migration of old representations is required in C5.2.

---
