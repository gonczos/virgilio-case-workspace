## C5.3.6 Result Note

Date:

2026-09-01

Scope:

Narrow read-only consultation enhancement exposing already-persisted PDF
evidence separately from ordinary interpretation representations.

No schema changes.
No importer changes.
No processing-policy changes.
No new extraction.
No worker changes.

### 1. Inspection surface implemented

The existing consultation binary-detail path was extended so one page can
now show:

* original binary identity and context;
* ordinary interpretation representations;
* effective consultation selection and selection provenance;
* persisted PDF evidence representations as a separate read-only section;
* existing comparison/attention/provenance information.

The UI keeps interpretation and evidence visibly separate.

### 2. Routes/components/helpers changed

Runtime/API:

* `app/consultation-store.mjs`

UI:

* `ui/src/pages/BinaryDetailPage.tsx`
* `ui/src/components/EvidenceViewer.tsx`
* `ui/src/components/TechnicalDetails.tsx`
* `ui/src/types/consultation.ts`
* `ui/src/utils/consultation.ts`
* `ui/src/utils/consultation.test.ts`

Focused API coverage:

* `test/consultation-api.test.mjs`

No new consultation route was introduced.

### 3. Binary identity / provenance exposure

The existing binary detail response remains the inspection entry point.
It continues to expose:

* `file_binary` id;
* SHA-256;
* MIME type / file extension;
* machine-readability classification;
* page count and size where available;
* linked document/bucket/case/workspace context;
* processing summary and job list.

### 4. Original PDF access

Original PDF access remains through the existing binary-serving URL
already exposed in consultation detail:

* `binary.original_binary_url`

This checkpoint did not introduce direct filesystem-path exposure or a
new binary-serving path.

### 5. Evidence / interpretation separation

The consultation detail payload now separates:

* `representations.items`
  * interpretation representations only
  * currently `representation_kind = extracted_document_bundle`
* `evidence.items`
  * persisted PDF evidence representations only

This keeps:

* consultation selection semantics
* representation preference
* evidence visibility

distinct from each other.

### 6. Effective selection and provenance

Effective consultation selection still comes from the existing
representation-selection logic.

The detail payload continues to expose:

* effective representation id;
* processor key/version;
* `effective_selection_reason`;
* provenance `selection_source`;
* explicit selection record when present.

This checkpoint did not introduce a second selection algorithm.

### 7. Raw/native artifact inspection

The existing representation-content endpoint was reused:

* `GET /api/consultation/representations/:id/content?format=...`

That endpoint already works by representation id and was therefore able
to serve evidence representations without a new route.

Evidence inspection now uses that existing path for persisted formats
such as:

* `text`
* `native-json`

Interpretation formats such as `markdown` and `complete-text` remain
available where the selected representation provides them.

### 9. Read-only confirmation

Focused API coverage now asserts that a consultation detail request does
not create new `processing_job` rows.

This checkpoint:

* did not enqueue processing;
* did not invoke processors;
* did not create representations;
* did not change explicit selection state;
* did not require a worker to be running.

### 10. Validation performed

Focused tests:

* `node --test --test-concurrency=1 test/consultation-api.test.mjs`
* `npm --prefix ui run test -- src/utils/consultation.test.ts`

UI build:

* `npm run build` from `ui/`

The build completed successfully after one sandbox escalation needed to
reach the host Node/npm installation. Vite also reported that the
current Node version (`20.15.0`) is older than its preferred `20.19+`
baseline, but the build still completed successfully in this repository
state.

### 11. Known limitations

This checkpoint does not:

* compute a new diff view;
* summarize evidence-channel disagreement automatically;
* prove that an absent persisted evidence artifact means source-level
  absence;
* backfill evidence for older binaries that have not been rolled through
  the evidence processors;
* expose a dedicated document-first inspection route separate from the
  current binary detail path.

The evidence section currently reflects persisted availability only.

### 12. Recommended next step

Keep the next slice narrow and evidence-focused.

The most natural next step is a bounded rollout or inspection-improvement
slice that:

* expands persisted evidence coverage over a controlled representative
  set; or
* adds a compact disagreement/evidence summary layer over the now-exposed
  persisted artifacts;

without starting search, semantic extraction, or Phase D work.
