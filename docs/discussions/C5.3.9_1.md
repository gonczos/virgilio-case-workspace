Implement C5.3.9: portable export package inspection/verification.

Goal
----

Prove that a C5.3.8 export package is independently readable and verifiable
without database access, BinaryStore access, processor implementations, or
other live application state.

CLI
---

Add a sibling command to the existing `export-binary` command:

  node app/processing-admin.mjs inspect-export --package <dir>

Do not rename or reshape `export-binary`.

Important current constraint:

`app/processing-admin.mjs` currently opens a DB client and asserts the
processing schema before command dispatch.

`inspect-export` MUST work without DB access.

Therefore refactor the CLI entry path narrowly so commands that require the DB
still use the existing DB/bootstrap behavior, while `inspect-export` is
dispatched without opening a DB connection or asserting processing schema.

Do not introduce a broader CLI framework or unrelated command refactor.

Reusable reader/verifier
------------------------

Add a small reusable package-side reader/verifier.

It must operate only on the exported package directory.

Required behavior:

1. Parse `manifest.json`.

2. Validate the basic package structure required by the C5.3.8 contract.

   This must include:
   - `package_format` matches the C5.3.8 package format;
   - `package_version` is supported, and unsupported versions are rejected.

3. Validate package-local path safety before any existence or integrity
   verification.

   Validate only paths that the inspector uses to locate content inside the
   portable package.

   The following package-consumption paths must be package-relative and, after
   normalization/resolution, must remain inside the inspected package root:

   - `original_binary.package_path`;
   - each
     `manifest.package_contents.representation_artifacts[*].package_dir`;
   - each
     `manifest.package_contents.representation_artifacts[*].copied_files[*].relativePath`.

   Reject for those fields:

   - absolute paths;
   - malformed package-local paths;
   - `..` / traversal that escapes the package root;
   - any resolved path outside the inspected package root.

   Perform these checks before existence or integrity verification.

   Do NOT apply package-relative/path-containment requirements to persisted
   source metadata such as representation `artifact_rel_path`.

   `artifact_rel_path` is preserved C5.3.8 provenance/debug metadata
   describing the persisted source representation. It is not a
   package-consumption path and must not be resolved by the inspector to read
   package contents.

   Artifact consistency verification must instead correlate persisted
   `artifact_rel_path` with the corresponding entry in
   `manifest.package_contents.representation_artifacts`, and then use that
   entry's package-local `package_dir` /
   `copied_files[*].relativePath` fields when accessing exported artifacts.

4. Locate the exported original binary.

5. Independently recompute and verify:
   - SHA-256 against canonical `file_binary.sha256`;
   - byte size against the canonical recorded size.

6. Verify persisted representation artifacts consistently with the current
   C5.3.8 package contract.

   C5.3.8 records copied artifact sets in:

     manifest.package_contents.representation_artifacts

   and persisted representations may carry:

     artifact_rel_path

   Verify BOTH directions:

   a. every artifact file listed in
      `manifest.package_contents.representation_artifacts`
      exists inside the package;

   b. every persisted representation with a non-null `artifact_rel_path`
      has a corresponding package artifact entry.

   Fail clearly if either side is inconsistent.

   Do not invent artifact hashes or integrity guarantees not present in the
   current export contract.

7. Report useful inspection data, including:
   - file_binary identity;
   - original relative path;
   - representation count;
   - processing_job count;
   - persisted comparison/selection presence or counts;
   - derived.effective_selection;
   - representation identities;
   - persisted artifact paths/files.

8. Treat unprocessed exports honestly:
   - zero representations is valid;
   - zero processing jobs is valid;
   - no comparisons/selections is valid;
   - no processing state may be manufactured.

9. Fail explicitly for at least:
   - malformed/missing manifest;
   - unsupported `package_format`;
   - unsupported `package_version`;
   - missing original;
   - malformed, absolute, or package-escaping
     `original_binary.package_path`;
   - original SHA mismatch;
   - original size mismatch/truncation;
   - malformed, absolute, or package-escaping
     `representation_artifacts[*].package_dir`;
   - malformed, absolute, or package-escaping
     `representation_artifacts[*].copied_files[*].relativePath`;
   - missing manifest-listed artifact file;
   - representation with non-null persisted `artifact_rel_path` but no
     corresponding package artifact entry.

Architecture constraints
------------------------

The package reader/verifier and `inspect-export` path must not depend on:

- DB client creation;
- processing-schema bootstrap/assertion;
- BinaryStore;
- processor implementations;
- live representation state.

Keep the DB-bypass refactor minimal and command-specific.

Do not broadly change the export format.

If one small metadata gap genuinely blocks verification:
- document it first;
- make only the minimum compatible C5.3.8 correction required;
- do not broaden the package contract.
