## C5.3.3 Result Note

Date:

2026-09-01

Scope:

Narrow operational processing-policy correction following the bounded
C5.3.2 24-PDF rollout sample.

No schema changes.
No canonical-domain changes.
No representation-semantics changes.
No UI changes.
No broader rollout.

### 1. Timeout ownership findings

The previously observed 15-minute timeout came from the Python-extractor
subprocess wrapper in `app/processing-registry.mjs`.

Before this checkpoint:

* `runExtractor(...)` in `app/processing-registry.mjs` owned a shared
  `timeoutMs = 900000` budget for Python-backed processors.
* That shared budget applied to:
  * `docling`
  * `xberg`
  * `pdf_ocr_text`
* PDF evidence CLI processors used a separate path in
  `app/pdf-evidence.mjs` with `DEFAULT_TIMEOUT_MS = 120000`.

Therefore the old timeout policy was split across two layers:

* Python extraction adapters in `processing-registry`
* local evidence-tool CLI wrappers in `pdf-evidence`

This checkpoint made processor-specific timeout policy explicit and
passed those timeout values through both paths.

### 2. Previous concurrency behavior

Before this checkpoint:

* one worker processed one job at a time;
* multiple workers could be started independently;
* `claimNextJob(...)` was effectively FIFO by `requested_at, id`;
* there were no processor-specific concurrency limits;
* cheap evidence jobs competed for the same worker capacity as heavy
  jobs;
* Docling and OCR could run concurrently if multiple workers were
  started;
* multiple heavy jobs could therefore contend for local CPU/RAM at the
  same time.

The bounded sample strongly suggested that the previous failures were not
well explained by “15 minutes is always too short” alone.

### 3. Execution policy implemented

The new explicit built-in execution policy is:

* `plain_text_passthrough`
  * class: `fast`
  * claim priority: 500
  * timeout: 120000 ms
  * `max_attempts = 1`
* `pdf_literal_text`
  * class: `fast`
  * claim priority: 400
  * timeout: 120000 ms
  * `max_attempts = 1`
* `pdf_signature_metadata`
  * class: `fast`
  * claim priority: 390
  * timeout: 120000 ms
  * `max_attempts = 1`
* `pdf_structure_inventory`
  * class: `fast`
  * claim priority: 380
  * timeout: 120000 ms
  * `max_attempts = 1`
* `xberg`
  * class: `moderate`
  * claim priority: 300
  * timeout: 600000 ms
  * `max_attempts = 1`
* `docling`
  * class: `heavy`
  * claim priority: 200
  * timeout: 2700000 ms
  * `max_attempts = 1`
  * concurrency group:
    `shared_heavy_pdf_processing`
  * max concurrent in group: 1
* `pdf_ocr_text`
  * class: `very_heavy`
  * claim priority: 100
  * timeout: 2700000 ms
  * `max_attempts = 1`
  * concurrency group:
    `shared_heavy_pdf_processing`
  * max concurrent in group: 1

### 4. Heavy shared concurrency = 1

This checkpoint implemented one shared heavy concurrency group covering:

* `docling`
* `pdf_ocr_text`

Only one job in that group may be claimed as `running` at a time.

The implementation uses a PostgreSQL advisory transaction lock together
with running-job counting inside `claimNextJob(...)`.

Cheap evidence jobs remain claimable even when a heavy job is already
running.

### 5. Timeout/error handling

Timeout failures are now persisted distinctly as:

* `processor_timeout`

instead of collapsing into:

* `processor_failed`

This applies both to:

* Python extractor subprocesses
* PDF evidence CLI subprocesses

Timeout handling still terminates the child process with `SIGTERM`. No
orphan extractor/worker process remained after the targeted retry runs.

### 6. Retry-provenance behavior

This checkpoint preserved historical failure provenance.

Key rule:

* built-in processing jobs now enqueue with `max_attempts = 1`
* a later retry creates a new job row instead of mutating the historical
  failed row into success

This preserves attempt history at the job-row level without adding a new
attempt-history table.

Existing successful representation identity remains unchanged:

* a controlled retry must not create a duplicate same-identity
  representation
* a controlled retry must not overwrite an existing successful
  representation

Focused tests were added for both behaviors.

### 8. Historical failures remain

Historical failed rows were intentionally preserved.

This includes:

* prior heavy timeout failures
* prior `pdf_signature_metadata` / `pdf_structure_inventory` failures
  caused by the already-fixed qpdf warning-exit-code handling issue

Those rows were not deleted, rewritten, or reclassified.

### 9. Operational conclusion

The targeted retries support the following conclusion:

* contention was materially involved in the observed heavy failures
* the old single 15-minute Python budget was too blunt
* page count alone is not currently a sufficient discriminator for heavy
  processing cost

The 190-page `text_pdf` Docling case completed comfortably under the new
policy, which shows that “large page count” by itself is not enough to
explain the old failures.
