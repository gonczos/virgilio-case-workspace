## 1. Objective

Validate the **implemented C5.3.1 PDF evidence boundary** across a representative real-document sample and determine where the first implementation policy is:

* working as intended;
* defective;
* too narrow;
* or correctly deferred.

This is a rollout/validation phase, not a second broad investigation.

The key question is no longer:

> Do these PDF evidence channels matter?

That is already established.

The actual question is:

> How well does the current C5.3.1 implementation behave across representative repository PDFs, and what does that imply for the next narrow step?

---

## 2. Phase Boundary

Treat the current implemented PDF-side stack as:

```text
immutable file_binary PDF
    ->
PDF evidence artifacts
    ->
interpreted document representations
```

Where:

* `pdf_literal_text`
* `pdf_signature_metadata`
* `pdf_structure_inventory`
* `pdf_ocr_text`

are evidence-preserving artifacts, and:

* `docling`
* `xberg`

remain interpretation engines.

Do not collapse them.

Do not select one as authoritative truth.

Do not silently reconcile disagreement.

3. How often does `pdf_literal_text` materially add evidence beyond Docling/Xberg interpretation artifacts?
4. Does the current OCR gating policy behave correctly for:
   * `image_only_pdf`
   * `mostly_image_pdf`
5. Are signature and structure inventories accurate across:
   * unsigned ordinary PDFs
   * signed PDFs
   * multi-signature PDFs
   * unusual/problematic PDFs
6. Are there concrete rollout failures that indicate:
   * an implementation defect in C5.3.1
   * a policy gap
   * or a deferred-channel opportunity
7. What is the next narrow step after this validation?

## 8. Material Addition Semantics

For this phase, “materially adds evidence” should remain a narrow rollout judgment, not a generic scoring framework.

Record objective comparison facts where practical, such as:

* text present/absent
* text lengths
* signature count
* structure/channel presence
* OCR applicability

Record `material addition` separately as a documented inspection judgment with a short reason.

Do not infer materiality from text length alone.

Examples that count:

* visible signature-appearance text present in `pdf_literal_text` but absent from Docling/Xberg
* OCR text present for an image-heavy PDF where interpretation text is missing or materially thinner
* structure/signature metadata surfacing forms/signatures not reflected in interpretation outputs

Do not build a general confidence model.

Do not automate truth selection.

Do not conflate:

* longer text
* with better interpretation
* or with higher legal importance

## 10. Validation Rules

Validate the current implementation, not a hypothetical redesign.

At minimum confirm:

1. the evidence processors run through the existing processing boundary
2. repeated execution does not rewrite representation identity incorrectly
3. expected artifact kinds and provenance are persisted
4. `pdf_structure_inventory` does not serialize failed inspection as false absence
5. `pdf_signature_metadata` does not imply legal or cryptographic validation
6. `pdf_ocr_text` only runs under the current bounded policy unless a tested and explicitly documented exception is required
7. existing consultation-facing behavior remains unchanged

Also verify repository checks such as:

* `git diff --check`
* relevant focused tests

Do not run expensive full-corpus processing for ceremony.

If C5.3.2 discovers an implementation defect, do not automatically fix it during rollout.
First classify and document it.

A trivial defect that prevents the validation itself may be fixed narrowly with regression coverage; otherwise leave the correction for the next bounded implementation checkpoint.
