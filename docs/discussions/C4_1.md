# Architectural direction

The next project stages should balance two goals:

1. provide a small, tangible consultation UI so the corpus and processing work can be inspected and demonstrated;

2. keep the primary architectural direction focused on search, reliable AI retrieval, provenance, and incremental semantic enrichment.

The UI must not become the main project.

The agreed broad roadmap is:

```text
A / B     Canonical corpus foundation                  COMPLETE
C1-C3.2   Processing + representations + storage       COMPLETE

C4        Corpus Consultation MVP

D         Search & Retrieval Foundation

E         Incremental Semantic Enrichment

F         Rich Review / Knowledge Workspace
```

Update the architecture documentation accordingly.

# D — Search & Retrieval Foundation

The old Phase D description predates C2/C3 and should be revised substantially.

It should no longer describe Phase D as introducing the first real PDF processor.

Extraction, processor execution, failure isolation, multiple representations, comparison and selection already exist.

The new Phase D should focus on turning selected representations into a searchable, provenance-aware corpus suitable for later AI retrieval.

---

## D1 — Search derivation and lineage model

Before broad indexing, define explicit lineage for search-derived content.

Conceptually:

```text
document_representation
        ↓
search_derivation
        ↓
search_chunk
```

A search derivation should be able to identify at least:

```text
input representation
derivation/chunking strategy
strategy/version
relevant configuration identity
creation time
status
```

Exact schema is NOT being designed in this roadmap task.

The important architectural principles are:

### Indexed data is derived data

Search chunks/index entries are not canonical evidence.

They originate from a specific immutable `document_representation`.

### Exact representation lineage

Every search derivation must identify the exact representation used as input.

Never silently reinterpret old indexed content as belonging to a newly preferred representation.

Example:

```text
Xberg representation 41
    -> search derivation A

later:

Docling representation 52 becomes effective
    -> search derivation B
```

Derivation A may remain for history/debugging, but normal retrieval should not pretend that it represents representation 52.

### Versioned/rebuildable derivation

Changing:

* effective representation
* chunking strategy
* chunker version
* materially relevant configuration

may require a new search derivation.

Do not mutate provenance away.

### Search infrastructure is a projection

PostgreSQL should retain enough derivation/provenance information that external indexes can be rebuilt.

Architectural principle:

```text
PostgreSQL
    = authoritative derivation/provenance state

search/vector indexes
    = disposable/rebuildable projections
```

Do not choose an external search technology in this roadmap task.

---

## D2 — Search-ready chunks

Derive useful searchable units from the selected/effective representation.

Prefer structure-aware segmentation where available rather than arbitrary fixed character windows.

Preserve useful provenance where possible:

```text
document
representation
source segment/element
page
ordinal
heading/context
```

Do not require semantic enrichment before search becomes useful.

---

## D3 — Lexical retrieval

Implement useful textual search over the corpus.

PostgreSQL full-text search should be considered as the initial low-complexity option before adding another infrastructure service.

The target capability is approximately:

```text
query
  ↓
text retrieval
  ↓
ranked chunks
  ↓
document + representation + source provenance
```

Support useful existing metadata filters where appropriate.

The purpose is to validate:

* chunk quality
* retrieval quality
* multilingual behavior
* filtering
* provenance
* navigation back to source material

---

## D4 — Semantic/vector retrieval

After lexical retrieval and chunk quality are understood, add embedding/vector derivations if justified.

Conceptually:

```text
search_chunk
    ↓
embedding derivation
    ↓
vector projection
```

Embedding output must also have lineage/version information, including the model/version used.

The vector index should remain rebuildable.

The eventual retrieval model may combine:

```text
lexical relevance
+
vector relevance
+
metadata/semantic filters
```

Do not select or implement the vector technology in this roadmap task.

---

## D5 — AI-serving / RAG

Once retrieval is demonstrably useful:

```text
question
   ↓
retrieval
   ↓
relevant chunks
   ↓
AI
   ↓
answer + provenance
```

A central invariant is:

> AI-supported claims/citations must be traceable through the retrieval/search derivation to the exact `document_representation`, canonical document context, and original binary.

Do not make AI output itself canonical evidence.

# E — Incremental Semantic Enrichment

Use the hybrid strategy.

Semantic enrichment should NOT block the initial search implementation.

Instead:

```text
                         ┌── search chunks
document_representation ─┼── embeddings
                         └── semantic derivations
```

These are complementary derived interpretations of the same representation.

Semantic enrichment should later improve:

* filtering
* ranking
* navigation
* timelines
* cross-document relationships
* AI retrieval/context

without requiring the original search foundation to be replaced.

---

## E1 — Semantic derivation framework

Use the same provenance philosophy as processing and search.

Conceptually:

```text
document_representation
        ↓
semantic_derivation
        ↓
semantic observations
```

Semantic observations are derived interpretations, not automatically canonical facts.

---

## E2 — High-value factual/document observations

Begin with relatively objective, useful signals such as:

```text
dates
court/process reference numbers
document references
named persons
organizations/institutions
courts
document-type signals
language
```

Avoid prematurely constructing a large legal ontology.

## E3 — Cross-document relationships

Later support evidence-backed relationships such as:

```text
document cites document
document refers to proceeding
appeal relates to decision
report concerns person
submission responds to submission
```

Relationships should retain provenance/evidence.

---

## E4 — Timeline/event candidates

Support extracted event candidates rather than asserting an automatically generated timeline as unquestioned truth.

Conceptually:

```text
representation
    ↓
event candidate
    ├── date/time
    ├── actors
    ├── description
    └── evidence/provenance
```

Human review may later confirm/correct these.

---

## E5 — Matters/topics

Introduce structured cross-cutting matters/topics only after enough corpus evidence exists to understand what taxonomy is actually useful.

Possible examples in this corpus might eventually include proceedings or themes such as Hague Convention issues, Article 11 follow-up, psychological evaluation, appeals, parental contact, etc.

Do not hardcode that taxonomy now.

# Interaction between search and later enrichment

Explicitly document this because it is an important architectural decision.

The hybrid strategy means enrichment must work with an already-indexed corpus.

Do NOT assume semantic enrichment requires replacing existing search chunks.

Instead, later semantic observations may:

* attach to documents;
* attach to representations;
* attach to specific chunks/source spans where appropriate;
* become retrieval filters;
* become ranking signals;
* create cross-document navigation;
* support AI context selection.

If enrichment logic changes, create/version new derivations rather than silently rewriting provenance.

Likewise, if the effective representation changes, derived search/enrichment state associated with the previous representation must be identifiable as non-current/stale rather than silently reassigned.

The exact stale/current mechanism is deferred to D1/E1 design.

# Cross-phase architectural invariant

The architecture should increasingly resemble:

```text
original binary
      ↓
document representation
      ↓
 ┌───────────────┬──────────────────┬─────────────────────┐
 │               │                  │                     │
search        embeddings       semantic enrichment   human interpretation
derivation    derivation       derivation
 │               │                  │
chunks         vectors       entities/dates/relations
 │               │                  │
 └───────────────┴──────────────────┘
                  ↓
          retrieval / AI
```

Every important derived result should retain enough lineage to answer:

> What exact representation and processing/derivation method produced this information?

Preserve the distinction:

```text
original binary          = canonical evidence

document representation  = machine/human interpretation

search chunk              = derived retrieval unit

embedding                 = derived retrieval projection

semantic observation      = derived interpretation

search/vector index       = rebuildable projection

AI answer                 = generated interpretation
```
